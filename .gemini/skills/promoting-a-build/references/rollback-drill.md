# Rollback Drill

A rollback procedure that has never been executed is a hypothesis. This file turns
it into a rehearsal that produces evidence, and states what a rehearsal must
include that a real rollback will not tolerate skipping.

## When to drill

- Before the first production release of a new service.
- After any change to the deploy mechanism, the registry, the reverse proxy, or the
  orchestration layer.
- Periodically thereafter, on a schedule short enough that the answer is still
  current — quarterly for an actively deployed service.
- Immediately after a rollback that was harder than expected. That is the signal
  that the procedure, not the incident, was the problem.

A drill on a schedule nobody keeps is not a drill. Put it on the same calendar as
the releases.

## Where to drill

**Not on the production deployment.** A drill on the live deployment is a real
rollback, taken on a schedule you chose, and it exercises the production database.
Drill against an environment that shares the *mechanism* and not the *consequences*:

| Property | Production | Drill target |
|---|---|---|
| Same deploy mechanism | yes | **yes — this is the point** |
| Same artifact registry | yes | yes |
| Same reverse proxy / ingress | yes | yes |
| Same database | yes | **no — a copy** |
| Real user traffic | yes | no |

The mechanism is what fails during a rollback: a missing digest, a retained-tag
mistake, a compose file that rebuilds, a migration that is not reversible. All of
those are exercised by a staging drill and none of them is exercised by a
rollback on a copy of production against a different deploy path.

## The drill

### 0. Record the starting state

```bash
# what is running, and what should return to it
docker inspect --format='{{.Config.Image}}' <service>
```

Write down the digest you are rolling **back to** before you touch anything. The
temptation during an incident is to pick "the previous one" from memory, and memory
is exactly what is degraded at that moment.

### 1. Take a fresh backup, and prove it is restorable

**A backup that has never been restored is not a backup.** It is a file. This is
not a philosophical position: restore tooling is frequently incompatible with the
data it claims to back up, and the incompatibility is discovered during the
incident it was meant to cover.

The drill is the cheapest possible moment to discover that, and the worst possible
moment to discover it during a real rollback.

```bash
# 1. dump
# 2. restore into a *fresh empty* database, never over the running one
# 3. compare object counts between source and restored copy
# 4. confirm the restore log contains no errors
```

Two rules that this project's own history makes concrete:

- **Never restore over the running database.** A restore script for a whole
  instance contains `CREATE DATABASE` and reconnect statements; replayed where the
  databases already exist, it connects to the *existing* database and starts
  writing into live data. Use a single-database dump into a new empty database.
- **Check the output, not the exit status.** A restore can report success while
  having skipped every constraint that the data violated, leaving a restored
  database with *less* integrity than the original. Assert the object counts
  against the source.

The generic form: a restore that exits 0 is necessary and not sufficient. Assert
what the restore was supposed to produce.

### 2. Perform the rollback

```bash
IMAGE=<registry>/<service>@sha256:<previous-digest> docker compose up -d --wait
```

Note whether this **rebuilt** or pulled. If it rebuilt, the drill has already found
a defect: the previous artifact cannot be redeployed, so this rollback is not a
rollback. Record it and fix the deploy mechanism before the next release.

### 3. Re-run the verification gates

This is the step that makes a rollback a *verified* state change rather than an
unverified one. A rollback that starts a container and stops there leaves the
original failure in place, because the original failure was never diagnosed — it
was only hidden by the old code.

Run the gate catalog from the `verifying-a-deployment` skill. At minimum:

- [ ] Health and readiness pass.
- [ ] A functional check passes — the real dependency path, not liveness.
- [ ] The digest actually running matches the previous digest.
- [ ] Error rate and latency returned to their pre-release values.
- [ ] No data written by the failed release is left in a state the old code cannot
      read. **This is the one most likely to be missed**: the new version may have
      written rows in a shape the old version does not understand, so rolling the
      code back does not restore function.

### 4. Restore forward

A drill that ends rolled back leaves the environment behind. Promote the newer
digest again, re-run the gates, and record the time it took — that number is the
one you will want during a real incident.

## Measure it

A drill produces one number worth keeping: **time from decision to verified
recovery**. Record it in the release notes or the runbook.

If it is measured and short, the procedure is real. If it has never been measured,
the honest answer to "how long would rollback take?" is "unknown", and that answer
is what a stakeholder deserves before a release, not after one.

## What a drill cannot tell you

State these limits, so the drill is not mistaken for more assurance than it gives:

- **It does not exercise a real incident's timing.** A drill is scheduled; an
  incident is not. The human factors are the untested part.
- **It does not prove the data is recoverable at the moment you need it.** A backup
  from an hour ago is a different artifact from one from a day ago, and the drill
  used whatever existed when it ran.
- **It does not validate the diagnosis.** Rolling back works whether or not anyone
  understood the failure. A rollback that becomes permanent is a postponement, and
  the cause is still there.
