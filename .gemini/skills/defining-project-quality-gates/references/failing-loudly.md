# Making Gates Fail Loudly

The failure semantics in the main skill, with the concrete shapes that cause silent
passes. Every entry here has shipped in a real project.

---

## 1. The partial script

**Shape**: a script runs several commands in sequence and its exit status reflects
only the last one.

```sh
# WRONG: exits 0 if the last command succeeds, whatever failed before it
psql -f schema.sql
psql -f grants.sql
echo "schema loaded"
```

**Why it survives review**: the script reads correctly, and it is only wrong when
something upstream fails — which is exactly when nobody is reading the output.

**Fix**: stop on the first error, always.

```sh
set -e
# and for the tools that need it explicitly:
psql -v ON_ERROR_STOP=1 -f schema.sql
```

The database client case is the important one, because it is *silent by default*:
without an explicit stop-on-error flag, it reports each error as it goes, continues
past it, and exits 0. A schema script whose fourth statement fails builds three
tables and reports success. The most expensive part is what happens next: the
environment is treated as deployed, and the missing table is discovered on the first
request that needs it.

## 2. The check that asserts nothing

**Shape**: a gate runs a tool and checks only that it exited 0.

**Why it is weak**: exit 0 means the tool ran. It does not mean the tool did what
was wanted. A diff tool that compares the wrong pair exits 0 on two different
schemas. A migration tool with no pending migrations exits 0 whether or not the
history is coherent.

**Fix**: assert the post-condition, in the system's own terms.

```sh
# not: "the command succeeded"
# but: "the expected object exists and has the expected shape"
psql -tAc "SELECT count(*) FROM pg_tables WHERE schemaname='public'"
```

**And prefer sets over counts.** A count can be right by coincidence: a script that
skipped every table after its first error can still leave the right number. Compare
the names.

## 3. The inverted expectation

**Shape**: a test asserts that an operation *succeeds*, where the correct assertion
is that it *fails*.

**Why it is the most serious kind**: the test passes, and it passes *because the
boundary is not there*. Every other green result from that test is void, and the
defect it was written to find is now invisible.

**What it looks like in practice**: a permission test that grants a role nothing and
then successfully performs an operation it should not be able to. A migration test
that applies cleanly to a schema it should not match. A validation test that accepts
input the rules forbid.

**The rule**: for every negative test, the assertion is that the attempt fails, and
the test is meaningless unless you have confirmed it *can* fail — by temporarily
removing the control and watching it go red. A negative test never observed
failing is not a test.

## 4. The swallowed exit status

**Shape**: a wrapper runs a command, logs the output, and returns 0 regardless.

**Why it survives review**: it is usually written to "make the pipeline continue",
which is a real need — and the continuation is unconditional.

**Fix**: separate the two cases deliberately. Non-blocking gates report a summary
and do not fail the run; blocking gates propagate. The mistake is a gate that is
*believed* to be blocking and is not.

## 5. The grep that matches nothing

**Shape**: output is validated by searching for an error marker, and the marker does
not match the tool's real format.

**Why it matters**: the validation is what turns "the command finished" into "the
command did not fail". A marker that never matches turns it back into the former,
while still reading as a check.

**The general case**: any output-based validation must be shown to match on a
*deliberately broken* run. Run it once against a known failure and confirm the
check goes red. A check that has never gone red is an assumption.

Note the related trap: some tools prefix their error lines with a source
identifier, so a pattern anchored to the start of the line matches nothing while a
pattern searching anywhere in the line works. Verify the anchor against real output.

## 6. The green run that tested nothing

**Shape**: a suite passes because every test was skipped, filtered out, or marked
as expected-to-fail, and the count of executed tests is not checked.

**Why it happens**: a dependency is unavailable, an environment variable is unset,
and the suite's convention is to skip rather than fail.

**Fix**: assert that the expected number of tests ran. A run of zero is a failure,
not a pass. Where skipping is legitimate, report the skipped count alongside the
passed count, and make skipping visible in the pipeline output.

## 7. The gate that is wired to nothing

**Shape**: a guard exists — a structural test, a lint rule, a check in a script —
that reads a file which is not the file the project actually uses.

**Why it is common and why it is invisible**: it was written against a path that was
later renamed, or a file that was generated and later removed, and nothing notices
because the guard still passes. **A guard that has never failed has not been
tested**, and this is the most likely guard to be quietly checking nothing.

**How to detect it**: change the file it reads and confirm the guard goes red. If it
stays green, it is not guarding. This is a two-minute check on each structural
guard, and it is worth doing whenever one is added.

## 8. The order-dependent suite

**Shape**: tests pass in isolation and fail together, or fail in a different order
than they were written.

**Why it happens**: shared mutable state. A fixture that writes to a database not
rolled back, a module-level cache, a file on disk, a sequence generator, a
temporary directory reused across tests.

**Why it is serious**: the failure is intermittent and therefore gets attributed to
flakiness and retried, which hides it permanently. An order-dependent suite is a
suite whose failures carry no information.

**Fix**: every test arranges and disposes its own state. Where isolation is
expensive, use a transaction that is rolled back per test. Detect it by running the
suite in a shuffled order, and by running each test alone.

---

## 9. The time-dependent test

**Shape**: a test passes today and fails next month, or passes on one weekday and
fails on another.

**Why it happens**: the test reads the current date, or depends on a window that is
open only part of the time — business hours, a weekend, a month boundary, a
maintenance window, a holiday calendar.

**Why it is serious**: the defect is in the test, and it is reported as a product
defect at the worst possible time, usually by a user whose data falls in the window
the test ignored.

**Fix**: inject the date. Every test that needs "now" takes it as a parameter with a
fixed default. Where the production code genuinely branches on the date, that branch
is worth testing explicitly with a known date rather than incidentally with
whatever day the suite runs.

## 10. The gate that is required and routinely bypassed

**Shape**: a required check is red often enough that merges proceed anyway — via an
admin bypass, a re-run that happens to pass, or a token that skips the whole
pipeline.

**Why it is the most corrosive**: it does not merely fail to help, it teaches the
team that red is negotiable. Every other gate's credibility degrades with it.

**Fix, in order**: make the check reliable first (see the flakiness section in the
main skill), then narrow it to only the checks that are genuinely reliable, then
protect the branch so bypass requires a deliberate, visible act. **Reducing the set
of required checks to a small, dependable core is better than requiring ten checks
of which three are flaky** — the dependable core keeps its meaning, and the flaky
ones run and report without blocking.

## The audit

For any gate in a project, these five questions:

1. **What does it assert?** Not "what does it run" — what claim does it make?
2. **How do I know it can fail?** Have I watched it go red on a deliberate break?
3. **What does its failure look like?** Can a reader act on it without asking anyone?
4. **Is its exit status honest?** Does the pipeline see what the gate saw?
5. **Is it blocking, and is that believed?** A check believed to be blocking and
   not wired to block is the most expensive kind.

If any answer is unclear, the gate is a report. That is a legitimate thing to have —
but it should be labelled as one, so nobody waits for it.
