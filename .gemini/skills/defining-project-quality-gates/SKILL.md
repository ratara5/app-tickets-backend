# Defining Project Quality Gates

**Input**: the project root, the language and its toolchain, and the question being
answered — either "which checks should exist" or "why did this get through". If the
toolchain is unknown, read the project's manifest rather than guessing.

**Core principle**: a gate's value is the defects it catches per minute it costs.
Put the cheap decisive checks first, and make every one of them fail **loudly** —
a check that reports success on failure is worse than no check, because it removes
the reason to fix the underlying problem.

This skill is tool-independent. The commands are given per stack in the adapter
table; the ordering, separation and failure semantics apply to any language.

## When to Use

- Setting up checks for a project, or inheriting a project whose checks are absent.
- A pipeline is slow, and someone proposes removing a check to speed it up.
- A check is flaky and being skipped "temporarily".
- A defect reached a shared environment and the question is which tier should have
  caught it.
- Deciding what runs on a developer's machine versus on the runner.

## Tier 0: the developer machine

Checks that run before a commit exists. Their purpose is to make the feedback
loop short enough that the developer acts on it.

The economics: a check costing under a second is run every time. A check costing
two minutes is run when someone remembers. Anything above that belongs on the
runner, no matter how valuable it is, because a valuable check that is skipped is
worth nothing.

| Check | Typical cost | Catches |
|---|---|---|
| Formatter | <1s | whitespace, import order, mechanical style |
| Linter | <2s | unused code, shadowing, suspicious constructs |
| Type check | 2–10s | wrong arity, wrong attribute, impossible states |
| Fast unit tests | <10s | logic regressions |
| Secret scan | <1s | committed credentials |

**Run these on commit, not on push.** On push, the code has already been written
against a mental model that the check would have corrected, so the value of the
feedback has already decayed.

### Secrets are the one tier that is never optional

A leaked credential is not a code defect that a later commit fixes. It is
compromised, and remediation is rotation plus history rewriting plus an audit of
where it went. The scan costs under a second.

It must be a **pre-commit** hook, not a runner job. A runner job means the secret
is already in the commit, and possibly already pushed.

## Tier 1: the commit

Everything in Tier 0, plus the checks that need more of the project than a working
tree provides.

| Check | Needs | Catches |
|---|---|---|
| Full unit suite | nothing external | logic regressions across the codebase |
| Coverage floor | nothing external | untested new code |
| Dependency audit | lockfile | known-vulnerable dependencies |
| Build the artifact | toolchain | code that no longer builds |
| Migration sanity | schema tool | a migration that cannot apply |

**The build gate is the one most often omitted, and the most expensive to skip.**
Code that passes every test and does not build is a common state, because tests
import modules and a build resolves them differently. A test suite is not a build.

**A coverage floor is a ratchet, not a target.** A floor applied to the whole
codebase at once fails on legacy code that nobody is working on, and the response is
to disable it. Apply it to **changed code**: new and modified lines must be covered.
That is enforceable in a diff and does not require anyone to fix old code first.

## Tier 2: the runner

Runs on every push and every pull request. This is where the checks that are too
slow or too stateful to run on every commit belong.

| Check | Needs | Catches |
|---|---|---|
| Integration tests | real dependencies | wrong queries, wrong transactions, wrong migrations |
| Schema drift gate | a database | models disagreeing with the live schema |
| Image build + scan | a builder | vulnerabilities in the image, not just the source |
| End-to-end suite | a running stack | the feature is actually reachable and correct |
| Contract check | both sides' specs | a breaking API change before the client finds it |

**Two separations matter more than the individual checks.**

### Checks that need a database do not belong in the unit tier

A unit suite that requires a database is not a unit suite: it is slower, it is
order-dependent because state leaks between tests, and its failures are ambiguous —
a broken test and a broken schema look identical. Keep the unit tier
dependency-free, and give the integration tier its own throwaway dependency.

This repository's history shows the cost of the alternative precisely: date-bound
tests failing only on certain days, and unique-constraint violations appearing only
in certain orders, both of which are state and time leaking into a suite that was
supposed to be neither.

**Time is a dependency too.** A test that depends on the current date is not
deterministic; it will pass in review and fail in three months, or pass on a
Tuesday and fail on a Saturday. Inject the date.

### Checks that mutate shared state are never in the default path

A destructive check is opt-in and explicitly named. The reasoning is the same one
that governs production: a check that runs by default will eventually run against
something it should not have.

## The failure-semantics rule

**A check that cannot report failure is worse than an absent check.** An absent
check is a known gap; a check that reports success while failing is a false
guarantee, and it is more expensive because it is trusted.

The specific, extremely common instance: a script that runs several commands and
reports success if the last one exited zero, when an earlier one failed. Its output
contains the error; its exit status does not. It looks green in a pipeline and
produces a broken release.

Requirements for every gate:

- **Fail on the first error** unless continuing is deliberate and the partial result
  is still checked.
- **Propagate the exit status** to the pipeline. No swallowing.
- **Assert the result, not just the completion.** Exit 0 proves the tool ran. It
  does not prove the tool did the right thing — a schema script that skipped every
  statement after its first error exits 0 with the wrong schema.
- **Report which check failed**, by name. A pipeline that prints one generic error
  for four checks costs more to debug than it saved.

The meta-rule that catches the whole class: **a check that passes when it was
expected to fail is a defect, and the highest-priority one.** A permission test that
succeeds, an isolation assertion that does not fail, a migration that applies
cleanly to a schema it should not match — each one means the check is not testing
what it claims, and every other green result from it is void.

## Ordering

Run the cheapest decisive check first. Two reasons, and the second is the one people
miss:

1. **Time to first failure.** A type error found in two seconds is fixed in two
   minutes. The same error found after a twelve-minute test run costs the developer
   twelve minutes of waiting, and they will start the run and walk away.

2. **Validity of later results.** If a check above fails, every check below it is
   running against code that is known-broken. Its results are noise. A twelve-minute
   suite after a failing type check is twelve minutes spent producing information
   nobody will use.

Recommended order, cheapest and most decisive first:

```
format → lint → types → fast unit → full unit + coverage → build
       → integration (needs dependencies) → migration sanity
       → end-to-end (needs a running stack) → image scan
```

Dependency-bound checks go last because they are the slowest to start and the
easiest to make order-dependent.

**Fail fast within a tier too.** `--exitfirst` on a failing suite, not
"run all 900 tests and print the last 50 lines".

## What does not belong in a gate

Some checks feel rigorous and are not worth their cost:

- **Tests asserting on log text.** Brittle, and they break on every refactor while
  catching nothing. Assert on behaviour, or on a structured field.
- **Formatting debates encoded as failures.** Handled by a formatter, once.
- **Coverage as an absolute number with no ratchet.** See above.
- **A gate that runs only on the default branch.** It must block before merge, or it
  is a report.
- **Anything destructive in the default path.**
- **Gates whose failure is routinely ignored.** A check that is skipped "temporarily"
  and has been for a month is worse than absent: it appears in the pipeline and
  trains the team to ignore red. If a check cannot be made reliable, remove it and
  say so, rather than leaving it to be bypassed.

## Flakiness is a defect with a ticket number

A flaky gate is not an inconvenience. It is a gate that has stopped carrying
information, and it is usually the beginning of the end: a team that learns a check
is unreliable stops reading it, and then stops running it.

Handle it as a defect, not as noise:

1. **Detect it separately** from correctness, so flakiness is visible as its own
   signal. A suite run many times, or a rerun policy that reports "passed on
   rerun", measures this directly.
2. **Quarantine, do not disable.** Move the test aside with a reason and an owner.
   A quarantined test is a visible debt; a silently skipped one is invisible.
3. **Fix the cause, don't retry.** Retry hides the flake in the numbers and keeps
   the cause in the code.
4. **Never increase retries to make a gate green.** That converts a visible flake
   into an invisible one and keeps the underlying defect forever.

The most common causes, in the order worth checking: real time or randomness in the
test, state leaking between tests through a shared resource, an assertion on
ordering or on an external service, and a resource that has not been released.

## Branch protection

A gate that can be bypassed is advisory. Merge must be blocked when the required
checks fail, and the set of required checks must be small enough that people do not
learn to bypass it — every required-but-flaky check pressures the team toward
unprotected branches.

Layered, in increasing strength:

| Layer | Provides | Limit |
|---|---|---|
| Local hooks | instant feedback | bypassable with a flag |
| Runner on pull request | the real verdict | bypassable by a maintainer |
| Required status checks | cannot merge while red | needs admin setup, and a token can bypass |
| No direct push to the protected branch | the invariant holds | friction for hotfixes; use a documented break-glass |

**Protect the main branch, not the feature branches.** Feature branches are cheap
and disposable; main is what everything else is built from.

## Making the gates runnable

Two properties decide whether a gate is actually used:

- **One command.** A developer and an agent must be able to run every gate with a
  single invocation, without knowing the internal order. Discoverable-by-inspection
  is discoverable by nobody.
- **The command is the same one CI runs.** A local gate that differs from the
  pipeline is a different gate, and the difference is always discovered in CI.

Provide these as a task runner, conventionally a `Makefile`, with targets of the
shape:

```
make setup     # one-time environment preparation
make test      # the unit tier
make lint      # format, lint, types
make gate      # everything CI runs, in order, fail fast
make run       # start the service locally
```

`make gate` must be the exact command CI invokes. If it is not, the pipeline is a
second, untested gate definition, and the local one — the one developers trust — is
the one nobody maintains.

## Guardrails

- Never add a gate that fails in a way nobody can act on. A gate must name the file,
  the line and the problem.
- Never let a gate report success when it failed. Propagate exit status; assert
  results, not just completion.
- Never put a database-backed or network-backed check in the unit tier.
- Never let a test depend on the current date, on randomness, or on execution order.
- Never increase retries to make a flaky gate green.
- Never mark a required check that the team routinely bypasses.
- Never make a destructive check part of the default path.
- Never let the local gate definition diverge from the one CI runs.
- Never treat coverage as an absolute target on a codebase with legacy code; ratchet
  the changed lines instead.
