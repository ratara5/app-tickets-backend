# Incident Review — the worked procedure

Run this after an incident. The deliverable is a change to the system or the
workflow, not a document.

## The anti-pattern this replaces

The review produces: a timeline, a list of contributing factors, and actions that
everyone agrees with and nobody completes. Three reasons that happens:

- **Blame language.** "Failed to check the database" suppresses the next report.
- **Actions with no owner or no completion test.** Unowned actions are not actions.
- **No check for a systemic cause.** The same incident recurs because the review
  found the trigger and not the condition that made the trigger reachable.

## The review questions

Answer all seven, in order, with the artifact named for each.

### 1. What did users experience?

Not "what failed" — what a user saw, for how long, and how many. Establish the blast
radius first: it determines whether this is an incident or a bug.

```
Users affected: <count or proportion>
Duration: <start → end, user-visible>
What they saw: <the failure as a user described it, not as a log describes it>
Secondary harm: <bad data written, retries charged, duplicates created>
```

**Secondary harm is the part that is usually missed.** A failure that wrote partial
data, duplicated work, or cached an error response produces a second incident later
during recovery, and it is invisible unless the review asks now.

### 2. Why did we not know earlier?

This is the question that makes observability improvements specific. Work backwards
from detection to prevention.

| Gap | Answer | Follow-up |
|---|---|---|
| Was there a signal before the impact? | yes / no | if no → missing instrumentation, name the exact signal |
| Did an alert fire? | before impact / at impact / never | if never → missing alert |
| Did an alert fire with a usable first action? | yes / no | if no → alert message or runbook |
| Did the runbook exist? | yes / no | if no → missing runbook, and name the command |
| Was the runbook accurate? | yes / no | if no → fix, and it is urgent |
| Could the responder diagnose from the signals? | yes / no | if no → name the missing log field or metric |
| Did detection depend on a customer reporting it? | yes / no | **if yes, this is the most important finding** |

The last row is the severity signal. Customer-reported detection means the entire
instrumentation chain is absent or broken, and every other finding is secondary.

### 3. What made the trigger reachable?

Separate the trigger from the condition. The trigger is what happened this time; the
condition is what made it possible.

> Trigger: the database connection pool was exhausted.
> Condition: nothing bounded the pool size, and no metric showed saturation before
> exhaustion.

A review that reports only the trigger produces an action about that one trigger,
and the next saturation has a different cause. Report both, and the action must
address the condition.

### 4. Which safeguards were absent, inert, or wrong?

| Safeguard | State | Why it did not stop it |
|---|---|---|
| Test that would have caught this | absent / present | |
| Deployment gate that would have caught this | absent / present / present but not run | |
| Alert that would have caught this | absent / present | |
| Health or readiness check | absent / present | |
| Review that would have caught this | absent / present | |
| Rollback or forward fix | how long did it take to stop the impact? | |

**"Present but not run" is the finding that repeats.** A gate that exists and was
skipped is not a testing gap; it is a process gap, and it needs a different fix.

### 5. How did detection and recovery take so long?

For each phase, the duration and what shortened it. The time from impact to
detection is the observability cost; from detection to mitigation is the runbook and
tooling cost.

| Phase | Duration | What would have shortened it |
|---|---|---|
| Impact → detection | | |
| Detection → diagnosis | | |
| Diagnosis → mitigation | | |
| Mitigation → full recovery | | |

The largest phase is where the next improvement goes. Teams routinely invest in the
easiest one.

### 6. What will we change, and how will we know it is done?

Every action needs all five. An action missing any of them will not be completed.

| # | Action | Type | Owner | Completion test | By when |
|---|---|---|---|---|---|
| 1 | | test / gate / code / observability / runbook / process | a person | a command that fails before and passes after | a date |
| 1 | Add a saturation metric for the connection pool | observability | | `metric` exists and a dashboard panel shows it | |
| 2 | Alert when pool utilisation exceeds 80% for 5 minutes | observability | | the alert fires in a test environment | |
| 3 | Add a gate step asserting readiness after deploy | gate | | `make verify` fails against a broken build | |
| 4 | Bound the pool size and document the sizing | code | | the value is in configuration with no default | |
| 5 | Runbook: database saturation | runbook | | a colleague follows it unaided in under 5 minutes | |

Rules for actions that hold:

- **Types are not interchangeable.** A test does not replace observability; an alert
  does not prevent a bug. Classify honestly, or the team will believe it is protected.
- **A completion test is a command.** "Improve monitoring" is not an action;
  `metric pool_saturation exists and is exported` is.
- **An action without a date is a wish.** Owner and date, or it does not go in.
- **Prefer an action that makes the failure detectable to the action that prevents
  it.** Detection is cheaper, always achievable, and works for the causes you have
  not thought of.

### 7. What changes permanently?

| Change | Where | Done when |
|---|---|---|
| New test | | fails before the fix, passes after |
| New gate | | `make verify` includes it |
| New alert + runbook | | fires in a test environment |
| Specification requirement | | the change is archived and synced |
| Document updated | | describes the current behaviour |

**The gate line is the one that converts a review into a system improvement.**
A test that is not wired into a gate will be skipped the first time it is
inconvenient.

## Severity

Determined by user impact, not by technical drama.

| Severity | Definition | Response |
|---|---|---|
| **S1** | core operation unavailable, or data is wrong or lost | page immediately; all hands |
| **S2** | core operation degraded, or a significant fraction of users blocked | page during business hours |
| **S3** | a non-core feature is broken, or a workaround exists | ticket |
| **S4** | cosmetic, or internal only | backlog |

Data wrongness is S1 even when nothing is unavailable. A user acting on a wrong
answer is worse off than one who received an error, and the harm compounds.

## The report format

Keep it short enough that it gets written.

```markdown
# Incident <id> — <one line: what users experienced>

**Severity:** S<n>   **Duration:** <start → end>   **Users affected:** <n>

## What happened
<3–5 sentences, user-visible framing>

## Timeline
| Time | Event | Source |
|---|---|---|

## Detection
<How we learned. If customer-reported, say so first.>

## Cause
**Trigger:** <what happened>
**Condition:** <what allowed it — the part that recurs>

## What we changed
<the action table>

## Follow-up
| Action | Owner | Due | Status |
|---|---|---|---|
```

## Follow-up discipline

- Review the action list at the start of the next incident review, before new
  actions are written. The existing list is why the incident recurred, and it is the
  first question.
- An action past its date is escalated, not re-dated.
- An action whose completion test cannot be written is not understood well enough to
  be started.
