# Triage Session — worked procedure

The main skill gives the rules. This is the sequence to run, and the artefacts to
leave behind. Adjust the thresholds to the project's size, not the other way round.

## Before the session

Produce the candidate list. Do not triage from memory — memory is where
already-fixed items hide.

```bash
# 1. everything open, with age
<tool> list changes            # or: ls openspec/changes
<tool> list proposals          # pre-proposals not yet formal

# 2. everything open whose tasks are already complete
<tool> view <change> --json    # or: grep -c '^\- \[x\]' openspec/changes/*/tasks.md

# 3. deltas that were never merged into the main specs
<tool> validate --all
ls openspec/changes/archive      # compare archived deltas against openspec/specs/

# 4. items filed against behaviour that may already have changed
<tool> list --sort created       # oldest first: the likeliest already-fixed
```

Step 2 is the highest-yield query in the whole procedure and takes seconds.

## The session

Work the candidate list in this order. Do not reorder by convenience; the order is
the point.

### Pass 1 — free progress

Everything that is complete or nearly complete:

- All tasks checked → verify → archive → sync the specification. **Count the
  archived.** This is the metric that tells the session whether it was worth having.
- Unsynced deltas found in step 3 → sync. No product decision required.
- Exact duplicates → merge, keep the clearest description, record both identifiers.

Anything in this pass needs no judgement. Do it first, while attention is fresh.

### Pass 2 — disposition

For each remaining item, one of the four fates. Record for every closure: what it
was, how it resolved or why not, when it was decided.

| Observation | Fate | Record |
|---|---|---|
| Behaviour is now correct | close as done | where the fix landed |
| Defect still reproduces | promote | the change to work next |
| Never was a defect; behaviour is intended | close as won't-do | the design intent that makes it intended |
| Superseded by another item | close as won't-do | the superseding item |
| Real, not now | defer | **the revisit trigger** |

Writing the intent into the "won't-do" record is what stops the same discussion
recurring. Without it, the next person re-raises it.

### Pass 3 — order the promotions

Rank by the leverage order in the main skill: security and data integrity first,
then blocking, then blocking-others-unsafe, then dependents waiting, then the rest
by size.

State the ordering explicitly in the session output. A ranking that is not written
down gets re-litigated, and the ranking is a decision that deserves visibility.

### Pass 4 — set the ceiling

Count what will be in progress. Compare to the ceiling.

- At or above the ceiling → the output of the session is **what to close**, and the
  session ends there.
- Below the ceiling → promote up to the ceiling, and only that many.

Never let pass 4 promote more than the ceiling allows, however obvious the next item
is. The ceiling's only function is to bind in exactly this moment.

## Outputs to leave behind

1. **Closure records** — what, how, when, for every closed item.
2. **A ranked promotion list** — with the ranking criterion stated.
3. **The unsynced-delta list**, or confirmation it is empty.
4. **A deferral list** where every entry has a revisit trigger.
5. **The open-item count before and after.** If the count did not fall, the session
   added work rather than finishing it, and that is the finding to report — not a
   reason to keep going.

Point 5 is the honest measure. A triage session that leaves the backlog larger is a
symptom of the workflow, not of the people running it.

## What to report to the requester

```
## State
Open items: <before> → <after>
Archived this session: <n>
Synced specifications: <n>
Closed as done: <n>   Won't-do: <n>   Deferred: <n>   Duplicates merged: <n>

## Next in line
<ranked list, with the criterion used>

## Deferred, with triggers
<item> — revisit when <trigger>

## Findings
<anything about the workflow that made finishing expensive — vague artifacts,
unchecked criteria, a missing sync step, a gate that is too slow to pass>
```

The findings section is the most valuable output and the one most often omitted.
Backlog growth is a symptom; the cause is in that section.

## Cadence

| Cadence | Focus |
|---|---|
| Weekly, short | pass 1 only — archive what is complete, sync what is unsynced |
| Monthly, longer | all four passes, including disposition of the oldest items |
| Before a release | all four passes, and no promotion until the backlog is closed down to the ceiling |
| On demand | after a change is abandoned, or when the open count jumps unexpectedly |

The weekly pass is short enough to always happen. The monthly pass is where
disposition happens, and it should never be combined with promotion — a session that
both closes and starts work will always net growth.
