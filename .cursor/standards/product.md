# Product Standards

Selected by the `product` bundle. The method is in the `product-strategy-analyst`
persona; this file is the short form an agent reads before deciding what to work
on.

## What an item needs before it is built

1. **A problem in the user's words**, before any solution vocabulary. A sentence
   naming a feature is a solution wearing a problem's clothes.
2. **A segment small enough to reach.** "Users" is not a segment.
3. **The existing workaround**, including "nothing" and "a spreadsheet". A built
   workaround is evidence the pain is real.
4. **The smallest thing that would prove or disprove it.**
5. **Named assumptions**, ranked by the cost of being wrong, each with the cheapest
   test.

An item missing these is not rejected — it is underspecified, and the useful
response is to name which one is missing rather than to guess at it.

## Triaging a backlog

Every item gets exactly one of four decisions. "Leave it" is not one of them; an
untriaged backlog grows by default.

| Decision | When |
|---|---|
| Promote | it unblocks other work, or it resolves a stated risk |
| Close | the specification now contradicts it |
| Defer | valuable and unready — state the condition that makes it ready |
| Discard | nobody will argue for it, including you |

Prefer deleting a stale specification to keeping it. A specification is a claim
about the system, and an untrue one costs every reader who trusts it.

## Evidence

- Mark every estimate as an estimate.
- Name the disconfirming case. A case that would prove the idea wrong is worth
  more than a third supporting one, and asking for it is what separates an
  analysis from an endorsement.
- Distinguish frequency from severity. A rare severe problem and a common mild one
  are different products with the same feature list.

## Writing it down

State the analysis in the response. When it belongs to a recorded decision, also
write it to `openspec/changes/<change>/product-analysis.md` — consumer state,
which no sync overwrites. Never write into `docs/`: that tree holds rules, not the
analysis that informed one decision.

## Vocabulary

This repository is the **harness**. A repository that pins a harness version is a
**consumer**. Not "project", not "app", not "downstream" — each of those is
ambiguous between the two, and an ambiguous noun in a standard becomes a wrong
projection in someone else's repository.
