# Frontend Standards (host-agnostic)

These invariants hold for every frontend host. They are owned here: a host
standard states only its delta and links back to this file. A rule that appears
in both places is owned here, and the host copy is an instance that a later host
revision removes.

The `frontend` bundle carries this file and the `frontend-developer` planner. Each
host bundle carries both as well as its own artifacts, so one selection delivers
the invariants and the delta together.

## 1. The contract is verified, not assumed

Read the published contract for every route, payload and error shape a plan
depends on. If it cannot be read, mark it unverified and list what must be
confirmed. A guessed shape produces a client that compiles, demos against a mock,
and fails against the real server.

## 2. One boundary carries calls to the server

Server calls go through one boundary that owns the base location, the credentials
and the error mapping. A view never constructs its own request. Every direct call
is a second place where all three live, and the second place is the one that goes
stale.

## 3. Server state and client state have one owner each

Name the owner of every value.

- **Server state** is anything the server is authoritative about. It is fetched,
  cached and invalidated by one mechanism. It is not copied into a client store on
  arrival; the cache is the store.
- **Client state** is session, preferences, draft input and navigation intent. It
  is written only by deliberate user action.

A value both claim is a value that will disagree with itself.

## 4. Every view declares loading, empty, error and success

A view states all four, and says what the user can do next in each. An empty
result set is not a loading state. A failure never leaves stale content presented
as current. A view that cannot state its error path is not finished.

## 5. Types come from the contract

Reuse the types generated from the contract. A hand-written parallel interface for
one payload drifts silently; the drift is invisible until a field is renamed. If
the contract cannot express a type, say which part is hand-written and why, and
type the boundary explicitly so a contract change fails where it is introduced.

## 6. Mocks are faithful to the contract and regenerated

A mock exists so a view can be developed before its server side does. Two
conditions make it safe:

- it is structurally faithful to the real contract, so a shape change breaks the
  mock rather than passing it;
- it is regenerated from the contract, not hand-maintained, so it cannot rot into
  describing a server that no longer exists.

A mock reproduces every branch of the contract, including the branch that does
nothing. The list of mock-backed features is the statement of what is still
unproven.

## 7. Localization is part of the screen

Every user-facing and accessibility string is declared in the localization source
and rendered through the translation function. The source language is the single
source of truth, and an engineer never authors a translation. A hardcoded visible
literal is a string the next language will not have.

## What the host standard owns

The host standard, not this file, decides:

- the layout and grouping of the host's source, where its tooling constrains it;
- the rendering and navigation model;
- the platform APIs and the mechanism for storage and credentials;
- the design tokens;
- the supported targets and runtime baseline;
- the verification commands and the evidence a change needs.

Naming a category here is not saying how the host implements it; the host standard
states the mechanism.

## What the consumer decides

The API contract, the domain vocabulary, the design tokens, the targets shipped,
and whether the client shares a repository with its server. The harness has no
opinion on those and never writes them.
