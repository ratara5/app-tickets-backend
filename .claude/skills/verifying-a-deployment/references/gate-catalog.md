# Gate Catalog — copy, adapt, keep

A concrete gate list to adapt. Every gate is a command with expected output, so it
can be run and recorded. Substitute the service's real dependency names; keep the
structure, which is ordered cheapest-and-most-decisive first.

Run order is deliberate: **a failure early means the later gates are meaningless.**
Verifying a functional path against an unhealthy process wastes the window in which
the real error would have been visible.

## Before deploying

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 0.1 | Working tree clean | `git status --porcelain` | no output |
| 0.2 | Revision is the one reviewed | `git rev-parse HEAD` | matches the approved commit |
| 0.3 | Quality gates green | your project's lint/type/test entry points | all exit 0 |
| 0.4 | No unapplied spec change | your spec tool's `status`/`list` | no change mid-implementation |
| 0.5 | Previous artifact still available | pull it, or read its digest from the registry | it resolves |

## Liveness

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 1.1 | Container is running | `docker ps --filter name=<svc>` | present and `Up` |
| 1.2 | **Restart count is zero** | `docker inspect --format='{{.RestartCount}}' <c>` | `0`, or rising is investigated |
| 1.3 | Startup completed | `docker logs <c>` | startup lines present, no repeating error |
| 1.4 | Runs as the intended user | `docker exec <c> id` | not uid 0 |
| 1.5 | Image is the intended one | `docker inspect --format='{{.Image}}' <c>` | matches the promoted digest |

**1.2 is the gate people skip.** A crash-looping container is `Up`. Restart count
is the only number that tells you it has been failing.

## Readiness

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 2.1 | Readiness endpoint | `curl -fsS http://<svc>:<port>/ready` | 2xx, quickly |
| 2.2 | Liveness is a *separate* route | `curl -fsS http://<svc>:<port>/live` | 2xx even when a dependency is down |
| 2.3 | Readiness reflects real dependencies | break a dependency, re-check | goes non-ready |
| 2.4 | Response is fast | `curl -w '%{time_total}'` | within budget |

2.3 is a destructive test, so run it deliberately and only where you own the
dependency. It is the only way to know readiness is not just returning 200.

## Functional — the layer that catches real defects

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 3.1 | Authenticated read | `curl` a real collection with a real credential | 200 and real data |
| 3.2 | Read is not empty by accident | inspect the body | contains the expected fields, not `[]` |
| 3.3 | Write path | POST, then GET the created resource | the created resource is returned |
| 3.4 | Datastore reached directly | query the datastore for the row written in 3.3 | the row exists |
| 3.5 | **Object storage round-trip** | presign an upload, send bytes, presign a download, fetch it | the bytes come back |
| 3.6 | Cache read/write | write, then read through a different path | consistent |
| 3.7 | Queue publish/consume | publish, then read from the consumer side | the message arrives |
| 3.8 | Third-party call | the real endpoint, with a stub-tolerant assertion | expected response shape |

**3.5 is the highest-value gate in the list and the most frequently skipped.** A
service whose signed URLs are wrong passes 1.1 through 3.4 and fails for every
user, because the failure is in a URL the *client* resolves. Fetch one from outside
and read the bytes.

**3.2 exists because 3.1 passes on an empty result.** A 200 with an empty list is a
green check on a broken query.

## Configuration resolved

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 4.1 | Startup log shows resolved config | `docker logs <c> \| head` | this environment's values, not defaults |
| 4.2 | Dialed endpoints resolve | from inside the container, resolve each host | all resolve |
| 4.3 | **Signed origins are client-resolvable** | fetch a generated URL from outside | it loads |
| 4.4 | No secrets in the image | `docker history`, config inspection | no credential is baked in |
| 4.5 | Filesystem is as intended | read-only where expected, writable volumes where required | matches the design |

4.2 and 4.3 are different addresses for the same dependency in most applications,
and forcing one value to serve both is a recurring defect. See
`references/dependency-failure-modes.md`.

## Isolation (shared estate only)

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 5.1 | Estate snapshot taken | record containers, networks, volumes, databases, buckets | recorded before the change |
| 5.2 | Diff after the change | diff the snapshots | only your own resources changed |
| 5.3 | Credential cannot reach another tenant's data | attempt it, as that credential | **the attempt fails** |
| 5.4 | No data port published | `docker ps` port listing | only the proxy is public |
| 5.5 | Application role is not an administrator | assert privilege attributes | query returns 0 rows |

**5.3 is the isolation claim, and it only counts if the attempt fails.** A test that
passes when it was expected to fail is a defect, not a pass — investigate it as the
most serious finding in the run.

## Observability

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 6.1 | Structured logs on stdout | read recent logs | parseable, with a correlation id |
| 6.2 | Request traceable end to end | make one request, find it by its id | one entry, correlatable |
| 6.3 | Error tracking receives errors | raise a deliberate error | it appears, in this environment |
| 6.4 | Uptime check targets the public path | check its configuration | not a container-local address |
| 6.5 | Alerts would fire | review thresholds against this release's risk | a plausible failure is covered |

6.3 is the gate that finds out that error tracking was never configured. Do it
deliberately and then remove the test error.

## Backup and restore

| # | Gate | Command shape | Passes when |
|---|---|---|---|
| 7.1 | Backup taken before shared state was touched | dump to a timestamped file | exists, mode 600 |
| 7.2 | **Restore verified into a fresh empty database** | restore, then compare | object counts match the source |
| 7.3 | Restore log has no errors | grep the log, filtered | empty |
| 7.4 | The drill did not touch the running database | read the command | a new database name, not the live one |

**7.2 and 7.3 are the ones that catch real problems.** A restore can exit 0 having
skipped every constraint the data violated, leaving a copy with less integrity than
the source. Compare counts; do not trust the exit status. And never restore over a
running database — instance-level restore scripts reconnect to existing databases
and begin writing into live data.

**These are shapes, not mandates.** The gate is the property being checked; the

project does not have will not be run.

## Minimal viable set

If the team will not adopt the full catalog, this is the floor. Everything above it
is improvement; nothing in it is optional.

1. **Restart count is zero** — the container is not crash-looping.
2. **Readiness passes.**
3. **One authenticated read returns real, non-empty data.**
4. **One write, read back, and confirmed in the datastore.**
5. **One round-trip through each external dependency** — the gate that catches
   media, storage and third-party failures.
6. **The running artifact is the intended digest.**
7. **The public entry point answers**, not only the container-local one.

Gates 3, 4 and 5 are the ones that have real outage coverage. A verification
process consisting of gates 1, 2 and 6 will report green through a total outage of
the feature the service exists to provide.
