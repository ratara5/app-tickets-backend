# Gate Tiers — concrete, per stage

Adapt these. Keep the ordering and the separations; substitute the project's
commands.

## Tier 0 — pre-commit (runs on every commit, on the developer machine)

Budget: under 20 seconds total. Anything slower stops being run.

| Order | Gate | Runs on | Why here |
|---|---|---|---|
| 1 | Secret scan | staged content | the only tier where a secret is still uncommitted |
| 2 | Format (write mode) | working tree | mechanical, zero decision-making |
| 3 | Lint | working tree | cheap, decisive |
| 4 | Type check (changed files where possible) | working tree | wrong types are the most common real defect |
| 5 | Fast unit tests (marked subset) | working tree | logic regressions on the changed area |

The order puts the secret scan first because it is the only check whose failure is
unrecoverable without rotation. Formatting comes before linting because a
formatter that can fix things should fix them before a linter reports them.

**If a check is skipped by an explicit flag, the flag is named.** `--no-verify`
should be a deliberate, visible act, not the path of least resistance.

## Tier 1 — push / pull request (the runner)

Budget: under 10 minutes to first failure.

| Order | Gate | Needs | Blocking |
|---|---|---|---|
| 1 | Format check (verify mode) | nothing | yes |
| 2 | Lint | nothing | yes |
| 3 | Type check (full) | nothing | yes |
| 4 | Unit suite, fail fast | nothing external | yes |
| 5 | Coverage on changed lines | nothing external | yes |
| 6 | Build the artifact | toolchain | yes |
| 7 | Dependency audit | lockfile | yes, above a severity threshold |
| 8 | Integration suite | throwaway dependencies | yes |
| 9 | Schema drift gate | throwaway database | yes |
| 10 | Migration apply + re-apply no-op | throwaway database | yes |
| 11 | Image build and scan | a builder | yes |
| 12 | End-to-end suite | a running stack | yes |
| 13 | Contract/spec compatibility | the API spec | yes if both sides are in this repository |

**6 and 10 are the two most commonly omitted and the two most valuable.** A test
suite is not a build: tests import modules, a build resolves them, and code that
passes every test can still fail to package. And a migration that has never been
applied to a real database is a script, not a migration — applying it twice and
confirming the second run is a no-op is the check that catches a migration that is
not idempotent, which is a defect that only appears on the second deploy.

## Tier 2 — merge to the release branch

Cheap, because the expensive tiers already ran on the pull request. This tier
exists to make the merge itself trustworthy.

| Gate | Passes when |
|---|---|
| All required checks green on the exact commit | the merge commit is a tested commit |
| The artifact for this commit exists and is pinned by digest | the release can promote it |
| No unapplied spec change is mid-implementation | the code matches an approved design |
| Previous artifact is still pullable | rollback is possible |

The last two come from the spec-driven workflow: merging code that belongs to a
change still being implemented, and merging without a rollback target, are both
states a pipeline can detect and neither is visible in a diff.

## Tier 3 — post-merge / release

Not a gate on the code, a gate on the release.

| Gate | Passes when |
|---|---|
| Artifact promoted by digest | the running artifact is the tested artifact |
| Verification gates from the deployment skill pass | the service works, not just runs |
| Previous digest still available | the release is reversible |

## What must never be a default-path gate

| Check | Why it is opt-in |
|---|---|
| Any check that writes to a database that is not created for the check | it will eventually run against a real one |
| Any check that calls a third-party service with side effects | it bills, sends or writes |
| Any check that deletes data | irreversible, and one wrong variable away from a real environment |
| Any check that mutates shared infrastructure | a test must never take down a neighbour |

These are named explicitly and invoked explicitly. A check that runs by default will
eventually run somewhere it should not, and the failure mode is an incident rather
than a red build.

## The tier assignment, reasoned

The question for any candidate check is: **what does it need, and what does it cost
to start?**

| Needs | Cheapest correct tier | Reason |
|---|---|---|
| nothing but the source | pre-commit | feedback decays with delay |
| the whole project resolved | push | too slow to run per commit at full scope |
| a database or a service | push, with a throwaway instance | not a unit test; must not be in the unit tier |
| a running stack | push or a release-candidate job | slowest to start; least decisive per second |
| a real environment | after merge | a verification gate, not a code gate |

Two misassignments to avoid:

- **A database-backed check in the unit tier.** It makes the suite order-dependent
  and its failures ambiguous, and it is the usual reason a suite becomes
  "flaky" when it is actually leaky.
- **A slow check on every commit.** It trains developers to batch or skip. A check
  run once a day catches a fraction of what the same check catches on every push.

## Reporting a red gate

A gate that fails must produce:

- **which gate** failed, by name;
- **the command** that reproduces it, runnable locally;
- **the actual output**, not a summary;
- **whether it is a new failure or a known one.**

That last point is the one teams get wrong, and it has a concrete cost: a
pre-existing failure discovered mid-task is indistinguishable from a regression
introduced by the work in progress, and the instinct is to fix the wrong thing or to
blame the change. Provenance is a one-minute check — run the same test at the base
revision — and it prevents both.
