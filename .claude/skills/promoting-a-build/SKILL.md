# Promoting a Build Through Environments

**Input**: the project root, the artifact produced by the build step, the target
environment, and the deploy mechanism. If any is unknown, discover it. Never invent
a registry, a tag or a digest.

**Core rule**: build the artifact once, then promote the *identical* artifact
through every stage. Between stages, only configuration changes. Never code, never
the artifact.

This skill is the doctrine for the release pipeline. It is deliberately
stack- and platform-agnostic: the deploy layer (Compose, Swarm, Kubernetes, a PaaS,
GitOps) changes, the promotion discipline does not. For the estate-specific
provisioning and tenancy rules, see the `deploying-backend-vps` skill; this skill
governs *what is promoted and how it is identified*.

## When to Use

- Releasing a build to staging or production.
- A deploy procedure builds the image on the target host. **Read
  "Rebuilding on the target host" below; that is the most common way this skill's
  core rule is violated, and it is invisible in review.**
- A rollback is needed and the question is what to redeploy.
- Deciding whether a local run is a production check or a production deployment.
- Tagging a release, or a change broke something and the culprit is being isolated.

## The failure this prevents

The pipeline's most expensive defect is not a broken build. It is **a build that
works, deployed as something nobody tested**. It happens when the artifact is
rebuilt at each stage, because then every stage is testing a *different* artifact
that happens to be built from the same source:

| Stage | What was actually tested |
|---|---|
| Pre-prod check | built locally, from a possibly dirty working tree |
| Staging | rebuilt on the staging host, from whatever was checked out there |
| Production | rebuilt again, at deploy time, from the deployed checkout |

Three builds, three chances to differ. A base image tag moved, a lockfile was not
used, a `pip install` without pins resolved a newer transitive dependency, a
`git pull` merged something unreviewed. Every one of these produces a production
release that passed every gate, because the gates ran against a different artifact.

**The rule that detects it**: if you cannot name the artifact that was tested, you
did not test an artifact.

## 1. Build once, identify immutably

A tag is a mutable label. A **digest** is content-addressed and cannot change under
you. Promotion means moving a digest; rollback means moving a digest back.

```bash
# Build and tag with the source revision, never with a moving label
docker build -t <registry>/<service>:<commit-sha> .
docker push <registry>/<service>:<commit-sha>

# Read back the digest the registry assigned. This is the identity you promote.
docker inspect --format='{{index .RepoDigests 0}}' <registry>/<service>:<commit-sha>
# <registry>/<service>@sha256:...
```

Two rules that are not optional:

- **Tag with the commit SHA, never `latest`.** `latest` is a moving label, so two
  environments pointed at it are not necessarily on the same code, and a rollback
  to it is not a rollback at all. `latest` makes the promotion graph unknowable
  after the fact.
- **The digest, not the tag, is what a deploy references.** A tag can be re-pushed
  by anyone with push access; a digest cannot.

Record the digest in the release notes. The release is then reconstructible: "prod
runs `sha256:abc…`, which is commit `3f2a9c1`."

## 2. Promote configuration only

What changes between stages is **configuration**: credentials, endpoints, feature
flags, replica counts, resource limits. What must not change: the artifact.

| Concern | Dev | Pre-prod | Staging | Production |
|---|---|---|---|---|
| Artifact | same digest | same digest | same digest | same digest |
| Config source | local file | local file | env / secret store | env / secret store |
| Secrets | fake | fake | real, non-production data | real |
| Data | seeded fake | anonymized copy | anonymized snapshot | real |
| Topology | may differ | as close to prod as possible | prod's | prod's |

Two failure modes hide in the "secrets" and "data" rows:

- **Real credentials in a non-production environment.** A staging environment with
  production credentials that can reach production is a production environment with
  a different URL. Prefer credentials scoped to what that stage can reach.
- **Real data outside production.** A copy of production data in a lower
  environment is a data-protection obligation, not a convenience. Anonymize, or
  generate structurally identical fake data. Where the domain makes anonymization
  hard, generate from a schema and distributions rather than copying rows.

## 3. Deploy by digest

```bash
# The deploy references the digest, so the artifact is fixed regardless of tags
IMAGE=<registry>/<service>@sha256:<digest>
docker compose up -d --wait          # with the image pinned to IMAGE
```

A deploy that re-resolves a tag is not promoting an artifact. It is deploying
"whatever that name points at now", which is a different statement.

**Verify after deploying that the running artifact is the intended one**, because
the manifest can disagree with the tag for reasons outside your control:

```bash
docker inspect --format='{{.Image}}' <running-container>     # image id on this host
docker inspect <registry>/<service> --format='{{json .RepoDigests}}'
```

The comparison that matters is the digest, not the local image id. Two hosts can
hold the same content under different local ids.

## Rebuilding on the target host

Read this before accepting a deploy procedure.

If a deploy file carries a `build:` section, the target host builds the image
during the deploy. That contradicts the core rule, and the consequences are
specific:

- **Rollback by digest is impossible.** There is no promoted digest; each deploy
  produces a new local image, and the previous one may already be pruned.
- **The artifact is not reproducible.** The build depends on the state of the
  checkout on that host, which is not the commit under review. `git pull` on a
  deploy host merges; it does not fast-forward to a known revision.
- **The build fails on the deploy path.** A network outage or registry rate limit
  becomes a deployment outage, on the host, at the worst time.
- **Two applications sharing a host can build different things from one commit**,
  because the build is not a pure function of the source.

The fix is to build and push once, and have the deploy file reference the image
rather than build it. Concretely: replace the build directive with an `image:`
reference pinned to a digest, and supply the digest through the environment or a
release file.

**When rebuilding is defensible**, and only in these cases:

- The build genuinely cannot be performed anywhere but the target architecture
  (cross-compilation for a different CPU architecture is the honest example).
- The environment is throwaway, and nothing downstream depends on identity.
- The project has exactly one environment and no promotion step at all, so there
  is no second build to diverge from.

If you accept a rebuild, record the decision and its reason. An undocumented
rebuild reads as an oversight and gets "fixed" by the next person in a way that
breaks the build on an air-gapped host.

## 4. Schema changes: expand, migrate, contract

Deploys and schema changes are separate steps, and their order is what makes a
rollback safe.

| Phase | Change | Old code | New code |
|---|---|---|---|
| **Expand** | add the new column/table, nullable or defaulted | works | works |
| **Migrate** | backfill existing rows | works | works |
| **Deploy** | switch the application to the new column | works (still reads old) | works |
| **Contract** | drop the old column/table | **broken** | works |

The rule this encodes: **at every moment, both the previous and the current
version of the application are able to run.** Only then is rollback a matter of
switching the artifact, and only then is a rolling deployment safe.

Two violations of it, both common:

- **Contracting in the same release that stops reading the old column.** The
  rollback path is now broken: rolling back the application finds the column gone.
- **A destructive change with no expand phase** — a rename done as drop-then-add,
  a narrowing type change, a `NOT NULL` added before every row satisfies it. Each
  one is a single step that cannot be reversed by redeploying.

A non-nullable column added to a table that already has rows fails or defaults
silently, depending on the tool. Adding it nullable, backfilling, then constraining
is three releases or three ordered steps, and it is the only version that can be
rolled back at each stage.

Migrations run as a **one-shot job** from the application, before the new code
serves traffic, built from the same source as the application. See the
`deploying-backend-vps` skill for the provisioning/migration separation and the
rules about running them through the application container.

## 5. Choosing a rollout strategy

Escalate only when the risk justifies the operational cost. This is the whole
decision, and the default should be the cheapest option that carries the risk.

| Strategy | Cost | Use when |
|---|---|---|
| Recreate (stop, start new) | seconds of downtime | internal tool, no traffic |
| Rolling | needs ≥2 replicas, needs a scheduler | default for user-facing services |
| Blue/green | double capacity briefly | irreversible migrations, risky changes |
| Canary | needs traffic splitting and metrics | a change whose failure is user-visible and gradual |

Notes that decide real cases:

- **A single-replica service cannot roll.** It has nowhere to send traffic while
  the new version starts. With one replica, blue/green (two sets of containers, a
  proxy switch) is the only zero-downtime option, and it requires spare capacity
  for the duration.
- **A schema change and a blue/green switch interact badly** if the migration is
  destructive: the blue instance is still running against a schema the green
  instance just changed. Expand/contract is what makes blue/green safe, which is
  why that discipline is stated before this section rather than after it.
- **Canary needs a metric that moves before users complain.** Without one it is a
  slow rollout, not a canary, and it buys nothing over a staged promotion.

**Do not adopt an orchestrator before the pain exists.** Compose on one host is
the right answer for a single service until you need autoscaling, many services,
multiple teams, or multi-region. The artifact discipline in this skill is
independent of that choice, so the promotion model can be introduced now and the
deploy layer changed later without reworking releases.

## 6. Roll back by redeploying the previous digest

Rollback is a promotion in reverse, and it is fast **only if** the previous
artifact still exists and is still referenced by digest.

```bash
# 1. What is running now
docker inspect --format='{{index .Config.Image}}' <service>

# 2. Redeploy the previous digest (from the release notes)
IMAGE=<registry>/<service>@sha256:<previous-digest> docker compose up -d --wait

# 3. Re-run the verification gates. A rollback is not proven by the container
#    starting; it is proven by the same gates that proved the release.
```

Rules that make rollback actually work:

- **Roll back code first.** A schema change that followed expand/contract keeps the
  old code working, so redeploying the previous artifact is sufficient. Rolling
  back the schema as well is a separate, riskier decision requiring a human.
- **Never roll back by mutating data.** Restoring a dump over live data, or
  dropping objects to "undo" a migration, is not a rollback and needs an explicit
  human decision plus a fresh backup first.
- **The previous artifact must still be in the registry.** Retention policies that
  keep only the last few tags destroy the rollback path. Keep enough history to
  reach back past a bad release — a week of artifacts is a reasonable floor.
- **Re-run the gates after rolling back.** A rollback that is not verified is an
  unverified state change, and the failure it was correcting may still be present.

## Local execution is verification, not deployment

Two combinations of "run it locally, with production settings" get confused, and
the difference decides whether anyone believes a release was tested.

| | Local + production settings | Real production |
|---|---|---|
| Users | none but the developer | real |
| Data | fake or anonymized | real |
| Uptime expectation | none | continuous |
| Failure cost | a wasted afternoon | an incident |
| Is it a deployment? | **No** | Yes |

Running the shipped artifact locally is one of the highest-value checks in the
whole pipeline, and it is still not production. The only exception is genuinely
self-hosted hardware, where "local" is a location rather than a test.

The two local modes differ in what they prove, and both are worth having:

- **Production build, no container.** Proves the code compiles, bundles and runs
  with production settings. It says nothing about the packaging, so it cannot catch
  a file missing from the image.
- **The exact image, containerized.** Proves the packaging too: what is in the
  image, which user it runs as, which files it can write, what its entrypoint
  resolves. This is the one that catches real defects, and it is the only local
  check that can substitute for staging.

A check that cannot distinguish "the image starts" from "the image can do its job"
is weak. See the `verifying-a-deployment` skill for the gate catalog.

## Gates at a glance

Promotion is permitted only when the stage's gate is green. A gate is a check with
recorded output, not an assertion.

| Stage | Gate to pass |
|---|---|
| Pre-prod check | the shipped artifact starts with production settings; health, readiness and a functional check pass; migrations apply to a copy of the previous schema |
| Staging | the same digest passes the end-to-end suite, a performance check, and a rollback rehearsal; a human approves |
| Production | health and readiness green; monitoring clean; the previous digest still available for rollback |

Each gate names the artifact it ran against. A gate that cannot name the artifact
did not gate anything.

## Guardrails

- Never deploy a moving tag. Reference a digest, and record it in the release
  notes.
- Never rebuild the artifact between stages. If the deploy file carries a
  `build:` section, that is a defect to fix, not a default to accept.
- Never promote a dirty working tree. The build input is a committed revision.
- Never put credentials in the image, in a compose file, or in version control.
  Inject them at runtime, per environment.
- Never let a lower environment hold production credentials *and* a network path
  to production. That is production with a different URL.
- Never contract a schema in the same release that stops using the old shape. The
  rollback path closes the moment you do.
- Never treat "the container started" as a passed gate.
- Never run a destructive data operation as part of a rollback without an explicit
  human decision and a fresh backup.
- Never adopt an orchestrator to solve a problem you do not have yet. The promotion
  discipline holds on any deploy layer.
