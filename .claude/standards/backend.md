# Backend Standards

What a consumer opts into by selecting the `backend` bundle. The layering
discipline is in the `backend-developer` persona; this file is the concrete
convention behind it. A consumer on another stack keeps every rule here and
replaces the nouns.

Rules about thresholds are stated as rules; values are the consumer's. A number
in this file is a number the wrong consumer inherited.

## Layers and where code goes

| Layer | Path convention | Owns |
|---|---|---|
| Interface | `app/api/routes/` | handlers, schemas, status codes, dependency wiring |
| Application | `app/services/` | use cases, orchestration, transaction boundaries |
| Domain | `app/domain/` | entities, invariants, value objects, domain errors |
| Infrastructure | `app/infrastructure/` | repositories, migrations, external clients |

Dependencies point inward. The domain imports nothing from the layers around it,
so a rule about an invoice does not need to know that invoices are stored in
PostgreSQL. These are conventions, not laws: a consumer's own standards win.

## Stack

- **Web** — FastAPI. Handlers are thin functions; dependencies are declared with
  `Depends()`; a router aggregates them and does no work itself.
- **Validation and settings** — Pydantic models at the boundary. Settings come
  from one typed model read from one source, and the resolved settings are logged
  at startup so "which value is it actually using" is answerable from outside the
  process.
- **ORM** — SQLAlchemy 2.0 declarative. Entities map to tables; repositories own
  queries. Services never import the ORM.
- **Migrations** — Alembic, one migration per schema change, never autogenerated
  against a live or shared database. Where there is no history, take a baseline
  first and treat it as the starting point.
- **Database** — PostgreSQL. Multi-tenant schemas isolate by role, not by revoking
  from your own role, which changes nothing.
- **Tests** — pytest, `httpx` for the async client, factories for test data,
  `testcontainers` where a real database is the only honest answer. Coverage
  tooling measures; the threshold is the consumer's.

## Responsibility per layer

One reason to change a class is one reason. When a change requires touching a
model, a repository, a service and a route, the class that owns too much is
named by that fact.

- Entities declare structure and the rules that belong to the data.
- Repositories do data access and nothing else.
- Services orchestrate use cases and hold the transaction boundary.
- Routes handle HTTP concerns only.
- Schemas handle serialization and validation only.

Services depend on repository *abstractions*, injected through the constructor, so
a use case can be exercised without a database. A service that constructs its own
repository is a service whose logic can only be tested against one.

## Entities, value objects, aggregates

- An entity has identity that persists across changes: a primary key that means
  the same row, not a row that looks the same.
- A join-table record is a value object: a compound primary key over its parents,
  carrying its own fields and no identity of its own.
- Business logic lives on the entity as domain methods, not in the service that
  happens to call it. A rule enforced in two services is a rule that will be
  enforced in one of them.
- Audit fields are part of the entity contract, not an optional mixin: who
  created a row, who last changed it, and when. Prefer server-side defaults so
  the database is the authority even if a client lies.
- Relations are declared on the model and loaded explicitly where they are used.

## Naming and typing

- `snake_case` for modules, functions, variables, tables and columns.
  `PascalCase` for classes. `UPPER_SNAKE_CASE` for constants.
- Annotate every boundary a value crosses, and always the return type. Prefer the
  `X | None` union over `Optional[X]` and `list[X]` over `List[X]` on any runtime
  the consumer supports.
- Import in three groups — standard library, third party, local — and use
  absolute imports inside the package, so a moved module fails loudly instead of
  importing a sibling by accident.
- A `helper` is a name that stopped describing anything; a `utils` module is where
  code goes when nobody decided where it belonged.

## Errors, logging, validation

- Domain errors name the rule that was broken. `HTTPException` in a handler is
  fine; raising it from a repository means the data layer knows about HTTP.
- Map domain errors to status codes in one place, consistently, rather than at
  each call site.
- Register global handlers so the error envelope is the same whatever raised it.
- Log structured events with the identifiers needed to reconstruct the request —
  a correlation id, the actor, the resource. A log line that cannot be correlated
  to one request is a line nobody will read during an incident.
- Validate in three places, each for a different reason: schemas at the boundary
  for shape, services for business rules, database constraints as the final net
  that holds when the code above it has a bug.

## API design

- Resources, plural, with the identifier in the path and the verb in the method.
  Sub-resources nest only where the child cannot exist without the parent.
- Every response is JSON, every list endpoint is paginated, and every protected
  route states its authentication requirement explicitly rather than inheriting it
  from a router-level dependency nobody can see from the route.
- Partial updates use `exclude_unset`, so an absent field means "not mentioned"
  and not "set to null".
- The OpenAPI document is generated from the route definitions, never maintained
  beside them. Export it for clients that need it offline.
- Set a timeout on every outbound call. A call with no timeout is a call that
  holds a worker until the other end gives up.

## Data access

- Every list response states how its relations are loaded. The default is N+1,
  and it only appears at realistic row counts, which is why it survives review.
- Index foreign keys and the columns a filter actually sorts or matches on.
- Read-only queries project the columns they return instead of loading entities.
- Batch writes inside one transaction rather than one transaction per row.
- Translate storage errors at the repository boundary, into domain errors that
  name the rule.

## Testing

- Files are `test_*.py`; names are
  `test_<unit>_<scenario>_<expected_result>`, so a failure names its own cause
  in the suite output.
- A test that needs a database gets a session that rolls back, and shares one
  fixture rather than building its own engine. Prefer a real database over a
  substitute when the substitute would have to imitate the parts being tested.
- Generate test data with factories that mirror the model, so adding a required
  field does not mean editing every test that constructs one by hand.
- Every feature gets the same five cases: the happy path, the error path, the
  boundary values, the validation rejection, and the integration path through the
  database or an external service.
- Mock at the boundary you own — the repository or the client — never inside the
  domain. Prefer a test double to a mock for anything with behaviour: a mock
  asserts you called it, a double tells you what happens next.
- Prove an invariant with a domain unit test that needs no database. A test that
  needs a full stack to check a rule is a slower test of less.

## Performance

Measure before optimising, and prefer the database over the process for anything
set-shaped: index first, cache second. Use timezone-aware timestamps, server-side
defaults, and async handlers for I/O-bound work. Serve stored files by handing out
a signed URL instead of proxying bytes through the API.

## Security

- Keep tokens minimal: subject, expiry, issued-at. Each extra claim is a piece of
  state that can go stale and contradict another system.
- Hash passwords with a slow algorithm, and make expiry configurable rather than
  compiled in.
- Validate ownership before every mutation. Authentication says who is asking;
  authorization says whether they may.
- Role checks live where the role is known, and every route states its
  requirement.
- Rely on the ORM's parameterisation rather than on string formatting. Validate
  uploads by content type *and* size, and sanitise any path derived from a
  filename so a client cannot address a key outside its prefix.
- Secrets arrive from the environment through one typed settings model, are
  validated at startup, and are never committed. A missing secret should stop the
  process at boot, not surface as a failed request later.

## Workflow

- Work on a short feature branch, keep it small, and get it reviewed before it
  merges. A branch that spans a refactor and a feature gets reviewed as neither.
- Commit messages are English, imperative, and describe what changed.
- Before a change is done: the consumer's tests pass, its linter is clean, its
  type checker is clean, and it is formatted. Those four are the consumer's
  configuration, not numbers chosen here.

## What the consumer decides, and the harness does not

Thresholds and names: coverage percentage, strictness level, timeouts, rate
limits, role names, table naming, and the domain vocabulary itself. The harness
states rules about them — do not invent one, surface it as an open question — but
never picks a value. A threshold in the harness is a threshold the wrong consumer
inherited.
