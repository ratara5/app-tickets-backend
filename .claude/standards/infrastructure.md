# Infrastructure Standards (generic stack conventions)

The decision procedure is in the `infrastructure-developer` persona. This file
names the concerns a consumer opts into by selecting the `infrastructure` bundle.

The distinction that organises everything here: **what a service depends on**
versus **what it computes**. A change to the first is an infrastructure change
even when it looks like a one-line edit, and it is reviewed as one.

## Ownership before edit

Before editing any file, establish who owns it. A file this consumer does not own
is not edited — it is reported, as a follow-up against the owning consumer.

A shared declaration looks wrong from here about as often as it looks right, and
editing it either does nothing or changes a file other consumers still depend on,
invisibly to them.

## Provider or consumer

Establish which side of each dependency this consumer is on, because the correct
arrangement is different and choosing wrong is expensive in both directions.

**Consumer of a shared estate.** Reach the same instance by the same route: same
container names, same network, declared external. Isolate by tenant object — own
database, own role, own bucket, own user, own credentials — never by instance.
Mount no shared volume, reuse no shared name, publish no dependency port, restart
no container it did not declare. Make the dependency a named, failing-fast step
rather than an assumption.

**Provider of a shared estate.** Expose one network. A provider whose database
and object store sit on different networks forces every consumer to attach to
both, and that topology then leaks into every consumer's configuration. Pin what
you provide, or you cannot offer parity with anything. A change to what you
provide changes someone else's behaviour, so surface it.

Forbidden on both sides: declaring a private copy of a dependency something else
already provides *and* joining the shared network; reusing a shared container's
name; editing a shared declaration to make your own environment work; and any
check that mutates state before asserting which tenant it is on.

## Configuration contracts

- One code path reads configuration in every environment.
- Every setting is required everywhere. A default is a value nobody chose.
- The same file name everywhere with different values, so the deployed
  configuration is what is read locally too.
- Log the resolved configuration at startup.
- When a value has an internal and a public form, require both. A fallback between
  them produces URLs signed for the wrong origin with no error.

## Schema and data

- A schema change runs once, in order, and is recorded. Never a side effect of a
  service starting.
- Provision a role that owns nothing and cannot create roles or databases.
- Seed generated data, structurally faithful. Never production rows, never real
  credentials.

## Local parity

A local environment earns its cost by resembling the deployed one in packaging,
configuration resolution, dependency versions and network boundary — in that
order of frequency, packaging last. Establish which side of each dependency the
consumer is on *before* deciding anything else.

Treat a stopped dependency as occupied: it still owns its ports, volumes and
names.

## What the consumer decides

Its cloud, its orchestration tool, its migration tool, its host names, its bucket
names, its credential plumbing, and its tenancy model. The harness names the
concerns and the failure modes; it never writes a value, and a provider name that
appears in a harness standard is a leak.
