# Base Standards

These rules apply to every change in every consumer that pins this harness. They
are rendered into the agent entrypoints; the consumer's own `docs/` holds the
rules specific to it.

## 1. How to work

- **One small step at a time.** Finish and verify a step before starting the next.
  A batch of unverified steps produces a batch of unverified errors.
- **Test first.** Write the failing test before the implementation, for anything
  new. A test written afterwards proves the code does what the code does.
- **Question every assumption and inference.** State it, or state that it is
  unverified. A plan that looks researched and rests on a guess is worse than one
  that admits the gap, because the guess is invisible to the reader.
- **Prefer the incremental change.** A focused diff is reviewable; a large one is
  approved in a hurry.
- **Flag repeated patterns** when you see them, and say whether you fixed them or
  only noticed them.

## 2. Language

Every technical artifact is in English: code and its identifiers, comments, error
and log messages, documentation, schemas, database names, configuration,
scripts, commit messages, test names, and issue titles.

## 3. Types and naming

- Type every boundary a value crosses. Hold the consumer's configured strictness
  rather than assuming it.
- Name things for what they are, not for the layer they sit in. A `plan` is a
  plan; a `helper` is a name that stopped describing anything.

## 4. What this harness owns, and what you own

This is the part worth reading twice, because getting it wrong wastes a cycle.

| Artifact | Owner | You may edit it? |
|---|---|---|
| agents, skills, commands, standards | the harness | **no** — change the harness and re-sync |
| `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `codex.md` | generated | **no** — every file carries a `GENERATED` header |
| `.claude/`, `.opencode/`, `.cursor/`, `.codex/`, `.gemini/` | generated | **no** — build output |
| OpenSpec commands and skills | the pinned OpenSpec CLI | **no** — re-sync with the pinned version |
| `docs/` | the consumer | **yes** — yours |
| `openspec/specs`, `changes`, `archive` | the consumer | **yes** — yours |
| application code | the consumer | **yes** — yours |

Every generated file begins with a header saying so. A file without that header,
outside the paths above, is yours. If you need to change a generated file, change
the harness, bump its version, and run `agentic sync` — a hand edit survives
until the next sync silently deletes it.

Sync writes projected paths and nothing else. It never writes `docs/` or
`openspec/`, and it never writes application code. A requirement that seems to
need it is misfiled; say so rather than widening sync's reach.

## 5. Skills

- Skills live in the harness. When a request matches one, load its `SKILL.md`
  before continuing, and load any `references/` it points at.
- The description of a skill is its trigger, not a summary. Match on the
  situation it names.

## 6. OpenSpec is the specification

- A change's artifacts — scenarios, requirements, `tasks.md` — are the design.
  Code follows them; it does not precede them and does not replace them.
- **A new request arriving after apply and before archive is a specification
  update first**, not a quick fix. In order: update the affected artifacts, run
  the artifact-generation step if one is needed, implement, then re-verify
  against the updated artifacts before archiving. Do not apply a code-only fix in
  that window.
- `openspec/specs` is the truth about the system as it is. An archived change
  that was never synced into it leaves a specification that is quietly false.
- **A task is completed by whoever executed the check.** Mark one done only after
  running the verification yourself and having its output in hand. Handing the
  command to the user and marking the box is the one move that makes the whole
  artifact a claim rather than a record, and it is the move most likely to be
  taken when the check is inconvenient.
- Record the pinned harness version on each change. It is how a reader knows which
  rules the work was written against.

## 7. Provenance

Commits and pull requests that carry harness-governed output carry the trailer:

```
Agentic-Layer: x.y.z
```

It is not decoration. It is how a future reader tells which generation of the
rules produced a file, and it is what makes a bisect meaningful.
