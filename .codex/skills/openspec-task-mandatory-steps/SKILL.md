# OpenSpec Task Mandatory Steps

**Input**: the change being shaped or applied — its proposal, specifications,
design, existing `tasks.md`, and the consumer's OpenSpec configuration.

**Core principle**: `tasks.md` is the execution contract, not a wish list. A
checkbox is a claim that the work happened and was verified. The agent that marks
it must be the agent that ran the check, and the evidence must outlive the
session. This skill makes that contract explicit and portable across stacks.

## When this applies

- **Task creation** — a fast-forward or continue workflow is about to write or
  replace `tasks.md` for a change.
- **Task updates** — new work is added, an existing task is reworded, or a task
  list is being finalized before implementation.
- **Task application** — an agent is working through the pending boxes in
  `tasks.md`.
- **After apply and before archive** — a request arrives while the change is
  implemented but not yet archived; see the post-apply rule below.

If the work touches none of these, this skill does not apply.

## Read the project configuration first

Before shaping or finalizing `tasks.md`, read `openspec/config.yaml`. The consumer
owns that file; the harness only reads it and never writes it. Treat what it
declares as authoritative:

| Declaration | What the task list must do |
|---|---|
| Branch naming convention | Use it for Step 0. |
| Mandatory verification steps | Include every step, in the declared order. |
| Report location and naming | Put evidence where the consumer expects it. |
| Documentation requirements | Include the documentation update in this change. |
| Any other mandatory step | Include it; do not summarize it away. |

Do not invent a verification step or substitute a command of your own choosing.
If `openspec/config.yaml` is absent, empty, or declares no mandatory steps, say
which declaration is missing and stop before finalizing the task list. A
configuration that is silent is a gap to report, not a licence to guess.

## The mandatory sequence

The order is part of the rule. A step that appears after a later step is not the
same procedure.

### Step 0 — Create and switch to the feature branch

Create the feature branch using the consumer's declared naming convention and
switch to it **before any implementation**. No implementation task may precede
this step. If the branch already exists and is current, record that instead of
creating a second one.

### Step 1 — Declare the mandatory steps in the task list

Read the configuration as described above. Add every declared verification and
documentation step to `tasks.md`, in the order the configuration gives them. Each
step must name what will be run or produced, not merely "verify".

### Step 2 — Implement

Carry out the change. Keep each task focused enough that its verification can
fail for one reason.

### Step 3 — Execute the declared verification

Run every declared verification step yourself (see the execution rule). Capture
the command output or the generated report. Do not move to the next task until
the current task's evidence exists.

### Step 4 — Update the documentation in the same change

If the change alters behaviour, an interface, or an operating procedure, update
the affected documentation as part of this change. Documentation is not a
follow-up; the change is not done while the documentation is stale.

### Step 5 — Run the final checklist

Run the checklist at the end of this skill before treating `tasks.md` as final.

## The execution rule

The agent MUST start what it can, run every declared verification itself, capture
the output, and then mark the task. It MUST NOT hand a check to the user — with
"please run this and tell me if it passes" — and then mark the checkbox.

If a check needs a running service, a clean database, a browser, or another
environment, start it or provision it when the repository and configuration allow.
If it genuinely cannot be started, report the blocker and leave the task open
rather than converting it into a request for the user. The underlying principle is
in `standards/base.md`; this skill states the operational consequence.

## The evidence rule

A task is complete only after the check ran and the report exists under the
change's `reports/` directory, with a date-and-step filename that identifies both
when the check ran and which task it covers. A task with no evidence stays open.

The report is evidence, not a second specification. It records what ran, what the
result was, and where the output lives. It does not restate the requirements and
it does not replace the task list.

## Post-apply requests are specification updates

A new request arriving after apply and before archive is a specification update
first. In order: update the affected OpenSpec artifacts, run the artifact
generation step if one is needed, implement, then re-verify against the updated
artifacts. Do not apply a code-only fix in that window, even when the fix looks
small; an unrecorded change makes the specification quietly false.

## Final verification checklist

Before finalizing `tasks.md` or declaring the change complete:

- [ ] Step 0 comes first: the feature branch was created and switched to before
      any implementation.
- [ ] Every mandatory step declared in `openspec/config.yaml` is present.
- [ ] The declared steps appear in the order the configuration gives them.
- [ ] Every verification was executed by the agent, not delegated to the user.
- [ ] Evidence for each completed task exists under the change's `reports/`
      directory, with a date-and-step filename.
- [ ] The documentation affected by the change was updated in this change.
- [ ] No checkbox is marked without the output or report in hand.
- [ ] No missing or contradictory declaration was silently filled in.

## Optional examples

These are illustrations only. The operative rule is always the consumer's
declared configuration.

- A declared HTTP check might start the service, call the endpoint, and capture
  the response.
- A declared browser check might drive the interface and capture the result.
- A declared database check might seed state, exercise the change, and restore the
  state afterwards.

Label each as an example in the task list, and point back to the configuration
for the actual command.
