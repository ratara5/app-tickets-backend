# Media and object storage — the contract that decides whether photos load

## Why object storage is mandatory, not optional

If a backend serves photos or PDFs from local disk, a container restart, a redeploy or
a second app instance loses them, and the failure is invisible until a user reports a
blank photo. Object storage is the only arrangement where the bytes outlive the
container.

- Bytes are written to a local staging path, then moved to object storage, then the
  local copy is deleted. If the move fails, the request fails; it never returns a URL
  pointing at a file that was already deleted locally.
- Clients receive **presigned** URLs, not credentials. A presigned URL grants access to
  exactly one object for a bounded time.
- The app is a signer and a mover, never a proxy for the bytes. A 4 MB photo passing
  through the API costs memory and bandwidth on every request.

## The `Host`-binding rule

Presigned URLs are signed for one scheme, host and port. This is the single most
common cause of "it works in the browser but the phone shows nothing":

| Configured endpoint | Client can reach it? | Result |
|---|---|---|
| internal container name | no | `403 SignatureDoesNotMatch`, or a DNS failure |
| public IP | usually not (NAT, firewall) | timeout |
| public hostname, correct port and scheme | yes | works |

So the app must hold the **client-facing** origin. Two ways to satisfy that without
giving up an internal name:

1. Resolve the public hostname inside the network to the storage container. Then the
   app can use a public-looking host internally too. On a user-defined Docker network,
   give the container a network alias equal to the public hostname.
2. Sign against the public origin while connecting over the internal address. Then the
   proxy in front of storage must forward the original `Host` header untouched.

Either way, **changing the endpoint invalidates every URL already delivered to a
client.** Decide the media host before the first release, and if it must change, restart
the app so new signatures use the new host.

## One bucket and one identity per app

Same rule as the shared database: a compromised or buggy app must not be able to reach
another app's objects.

1. **Bucket** — one per app, named for the app. Never reuse another app's bucket. If the
   app creates its own bucket on first boot, do not pre-create it; if you do, set it to
   private (no anonymous policy), since presigned URLs are the intended access path.
2. **User** — a dedicated MinIO user. A new user has no policies at all, and a service
   account inherits its parent's, so this user is what the policy attaches to.
3. **Policy** — bucket-scoped, least privilege:
   - bucket ARN: `s3:GetBucketLocation`, `s3:ListBucket`, `s3:ListBucketMultipartUploads`
   - object ARN: `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`,
     `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`
4. **Service account** — the keys the app uses, created from that user.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetBucketLocation", "s3:ListBucket", "s3:ListBucketMultipartUploads"],
      "Resource": ["arn:aws:s3:::<app-bucket>"]
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": ["arn:aws:s3:::<app-bucket>/*"]
    }
  ]
}
```

Run it from inside the storage container, which ships `mc`; the alias, the policy file
and the credentials then live in one container's filesystem and disappear together.

```bash
docker exec -it <minio-container> sh
mc alias set local http://127.0.0.1:9000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD"
mc admin user add local <app-user> '<generated-secret>'
cat > /tmp/policy.json <<'JSON'
{ ...as above... }
JSON
mc admin policy create local <app-policy> /tmp/policy.json
mc admin policy attach local <app-policy> --user <app-user>
mc admin svcacct add local <app-user> --access-key '<key>' --secret-key '<secret>'
mc mb local/<app-bucket>          # only if the app does not create it itself
rm -f /tmp/policy.json
```

Two traps that cost hours:

- **Multipart.** Clients switch to multipart above roughly 5 MiB, and multipart needs
  the two bucket-ARN and three object-ARN actions above. Without them, small uploads
  succeed and large ones fail with `AccessDenied` — which reads as a size-limit bug.
- **Wildcards.** `s3:*` on the instance, or an anonymous download policy on the bucket,
  defeats the isolation the dedicated identity exists to provide. Presigned URLs mean
  you never need public read access.

## CORS: when it is actually required

CORS is enforced by **browsers only**. It is irrelevant to native mobile clients.

| Path | Needs bucket CORS? |
|---|---|
| Native app fetches a presigned URL | **No** |
| Native app uploads via `POST` to its own API, which then talks to storage | **No** |
| Browser uploads directly to storage with a presigned PUT | **Yes** |
| Browser reads a presigned URL with `fetch`/XHR | **Yes** |
| Browser renders a presigned URL in `<img>` | **No** — image loads are not CORS-checked |
| Browser previews a PDF in an `<iframe>`/`fetch` | **Yes** |

So: mobile-only backend, skip it. Any browser client talking to storage directly, set it
on the **bucket** so other tenants on the same instance are unaffected:

```bash
cat > /tmp/cors.json <<'JSON'
{"CORSRules":[{"AllowedOrigin":["https://<app-domain>","http://localhost:<dev-port>"],
 "AllowedMethod":["GET","PUT","POST","HEAD"],"AllowedHeader":["*"],"MaxAgeSeconds":3000}]}
JSON
mc cors set local/<app-bucket> /tmp/cors.json
mc cors get local/<app-bucket>
rm -f /tmp/cors.json
```

The server-wide `MINIO_API_CORS_ALLOW_ORIGIN` environment variable is the alternative.
It applies to every bucket in the instance, so on a shared box prefer the bucket-scoped
configuration, and only change the server variable when you accept the effect on all
tenants. If a direct browser upload fails while an API-proxied upload of the same file
succeeds, CORS is the first suspect.

## Durability — the part that loses money

Object storage is not a backup. Back up to a **different failure domain** with its own
credentials.

```bash
# One-off before a risky change: a local copy on the box.
docker exec <pg-container> pg_dumpall -U <admin-user> > /root/pg-backup-$(date +%F-%H%M).sql
chmod 600 /root/pg-backup-*.sql
grep -c "CREATE TABLE" /root/pg-backup-*.sql    # a dump with no CREATE TABLE is worthless

# Continuous mirror: a separate alias with its own, bucket-scoped credentials.
mc alias set remote https://<backup-host> '<backup-key>' '<backup-secret>'
mc mirror --watch --overwrite remote/<app-bucket> local/<app-bucket>
```

- A `pg_dumpall` taken as a different OS user than root is not readable later; write it
  somewhere with a known owner and `chmod 600`.
- A backup you have never restored from is a hypothesis. Rehearse the restore.
- A mirror in the same failure domain is a copy, not a backup.

## Capacity

- Track bucket growth; presigned URLs expire but objects do not.
- Track the staging directory separately. It fills during concurrent uploads and empties
  on success; a disk that fills breaks uploads while the app still reports healthy.
- Multipart uploads that are aborted cost nothing but an incomplete part; a crashed
  client that never aborts leaves billable parts behind. Enable bucket lifecycle expiry
  for `AbortIncompleteMultipartUpload`.

## Verification, in order

```bash
mc stat local/<app-bucket>/<object>                       # exists, right size
mc admin policy info local/<app-policy>                   # what the identity may do
docker exec -it <minio-container> sh -c 'mc ls local'     # the app sees its bucket
```

Then the only test that counts, from a network that is not the server: presign an
upload, `PUT` real bytes, presign a download, fetch it back, compare, delete. Then repeat
it through the client app. Health checks pass while media is broken; only this catches
it.
