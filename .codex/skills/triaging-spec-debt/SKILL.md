# Triaging Specification Debt

**Input**: the full list of open items — proposals, pre-proposals, tickets, changes
with incomplete tasks — and the state of the main specifications.

**Core principle**: a specification is a claim about the system. It stops being a
claim the moment it diverges, and it is worth far less than nothing after that,
because it is trusted. Debt here is not a list of unfinished work; it is a growing
gap between what the documents say and what the system does.

This skill is tool-independent; where it names a specification tool, read the row
for your tool in the adapter table.

## When to Use

- The number of open items has grown and none is being closed.
- A change has been open for weeks with tasks incomplete.
- Delta specifications exist that were never merged into the main specifications.
- Nobody can say what the system currently does without reading the code.
- Before planning a quarter, or before a release, to know what is actually outstanding.

## The four fates

Every open item gets exactly one. The failure mode is items that stay open
indefinitely because closing them requires a decision nobody made.

| Fate | When | Action |
|---|---|---|
| **Promote** | real, worth doing, understood | becomes a change with artifacts, and gets worked |
| **Close as done** | already fixed, and the fix is verified | verify, then close and record where the fix landed |
| **Close as won't-do** | real, but not worth doing, or superseded | record the decision and the reason, so it is not re-raised |
| **Defer** | real, but not now | keep it, with a stated revisit trigger |

**"Close as done" requires verification, not recollection.** The most common error
in a backlog is closing something as fixed because it looks fixed. Check the actual
state — the behaviour, the test, the file. A backlog full of confidently-closed
items that were never fixed is worse than a long backlog, because it removes the
reminder.

**"Close as won't-do" is a real outcome and should be recorded.** An item closed
without a reason reappears in three months as a new proposal, and the discussion
starts again from nothing.

**Deferral needs a trigger.** "Later" is not a decision; it is an absence of one. A
deferred item states what would make it current again: a dependency landing, a
volume reaching a threshold, a date, an incident.

## The triage procedure

### 1. Establish the real state

Before triaging anything, know what the system does. Read the main specifications
and compare them against the code, at least for the areas with open items.

The specific check that pays for itself: **are there delta specifications that were
never synced?** A completed change whose delta was never merged leaves the main
specification describing the previous behaviour, permanently and invisibly. This is
the most common form of specification debt and the easiest to fix.

### 2. Classify by verification, not by description

For each item, one of three states — and this is a question about the system, not
about the document:

| State | How to tell | Fate |
|---|---|---|
| The defect exists | reproduce it, or read the code and find the defect | promote |
| Already fixed | the behaviour is correct now, verified | close as done |
| Never was a defect | the premise is wrong, or the behaviour is intended | close as won't-do |

The middle category is usually much larger than expected, and finding it is the
point of the exercise. Items were filed against a codebase that has since changed;
nobody closed them because closing required a decision.

### 3. Merge duplicates

Duplicates arise whenever two people notice the same problem. They are cheap to
merge and expensive to leave: two items for one defect produce two changes, two
sets of tests, and two chances to half-fix it.

Merge when the items describe the same underlying defect, even if the wording
differs. Keep the clearest description and record the other identifiers on it.

### 4. Order by leverage, not by age

Age is a poor proxy. Order by:

1. **It blocks other work.** A defect in a shared foundation blocks many changes.
2. **It is a security or data-integrity risk.** Always first, regardless of size.
3. **It makes other work unsafe.** A flaky gate or a non-reproducible build poisons
   everything downstream.
4. **It has a dependent change already waiting.**
5. Everything else, by size.

A large item that unblocks five others outranks five small independent ones, and
this is worth stating because the opposite is what happens by default: a team works
the smallest items because they are quick, and the blocking item is never the
quick one.

### 5. Bound the work in progress

Unbounded parallel work is the mechanism by which a backlog grows. Every open change
consumes attention, and attention is the constraint.

Set a limit and hold it. The limit should be small enough that items actually close.
A limit of three is usually right for one developer; the specific number matters
less than the fact that it exists and is enforced.

**When the limit is reached, the next action is closing something, not starting
something.** This rule is the whole skill. Without it, every triage session adds
items and the backlog is a record of triage sessions rather than of progress.

## Per-change health

For a change that exists but is not moving, the question is which of these it is:

| State | Signal | Action |
|---|---|---|
| In progress, actively being worked on | tasks completing | finish it |
| Started, then abandoned | no movement for weeks | decide: resume, or close it back to a proposal |
| Blocked on a dependency | tasks cannot proceed | record the blocking item explicitly |
| Artifacts incomplete | a required artifact is missing or thin | complete the artifacts before implementing |
| Effectively finished | all tasks done, not archived | verify, then archive |

**The last row is free progress.** A change with every task complete has already
cost everything it is going to cost; archiving it and syncing its specification is
minutes of work that removes an open item permanently.

**Abandoned changes are not free.** An abandoned change in the list is a proposal
nobody can find any more, because the reasoning lived in the conversation that
started it. Close it back to a proposal with its state recorded, or delete it with
the reason.

## What to record when closing

Every closure records three things, and the reason is that the next person
encountering the same problem needs the answer faster than they can re-derive it:

- **What it was** — one sentence, so it can be recognised later.
- **How it was resolved, or why it will not be** — with a reference to the change,
  commit or decision.
- **When it was decided** — because "we decided not to do this" expires, and someone
  should know how old the decision is.

## Adapter table — the same procedure per tool

| Concern | Spec-driven tools with changes and specs | Issue trackers | Plain documents |
|---|---|---|---|
| The unit of work | a change with artifacts | an issue | a proposal document |
| "Implemented" means | tasks complete and verified | linked change merged | code merged and documented |
| "Shipped" means | change archived **and** delta merged into the main spec | issue closed and deployed | the document updated to match the code |
| Merge deltas | the tool's sync step | n/a | manual, and therefore easily forgotten |
| Validation | the tool's validate command | the link checker, if any | none — the highest-risk case |
| Archive | the tool's archive command | close the issue | move the document |

**The distinction that matters in every column** is between *implemented* and
*shipped*. A change that is implemented but whose specification was never merged
into the main specification has produced a system the specifications do not
describe. Closing it as done at that point makes the gap permanent.

## The WIP ceiling, and why it is the whole point

A backlog grows when starting is cheaper than finishing. That is a rational
response to a workflow where finishing is hard — a change with vague artifacts, an
unclear acceptance criterion, a specification that has to be reverse-engineered from
the code.

So when a backlog grows, the fix is usually not discipline. It is to make finishing
cheap: artifacts that are complete enough to work from, acceptance criteria that can
be checked, a workflow where the last step is short.

The ceiling is the enforcement mechanism for that. A team that hits the ceiling is
forced to discover why closing is hard, which is the more valuable discovery.

## Guardrails

- Never close an item as done without verifying the system, not the document.
- Never leave a deferred item without a revisit trigger.
- Never start a new change while the work-in-progress limit is reached.
- Never let a completed change sit unarchived; it is free progress left on the
  table.
- Never archive a change whose delta specification was not merged into the main
  specification, and never call that "shipped".
- Never re-raise a decision that was already closed as won't-do without reading the
  reason first.
- Never keep a change open because closing it requires a decision, when the decision
  is a product question — escalate it instead. An open change is not how a product
  question gets asked.
