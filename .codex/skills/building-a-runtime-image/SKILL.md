# Building a Runtime Image

**Input**: the project root, the dependency manifest, the runtime command, the
health endpoint, the writable paths the service needs, and the migration command
if the project has one. If any of these are unknown, read the project before
choosing an image layout.

**Core principle**: the image is the artifact that ships, not a convenience
wrapper around the source tree. Build it in explicit stages, run it as a fixed
non-root identity, and keep only what the service needs at runtime. Everything
else is a defect that survives until an operator finds it in production.

## When to Use

- Authoring the Dockerfile for a new backend.
- Reviewing an image before it is promoted or deployed.
- A container starts but cannot import the application, write a file, or reach a
  dependency.
- A vulnerability scan or a size review finds a compiler, a test runner, or a
  package manager in the final image.
- A migration job and the runtime service are built from different source or
  different stages.

## The two-stage contract

Use one Dockerfile with two explicit stages built from the same source:

| Stage | Purpose | Runs as | Lifetime |
|---|---|---|---|
| `migrate` | apply the schema change | the elevated migration identity | a one-shot job |
| `runtime` | serve traffic | the unprivileged runtime identity | the service |

The runtime stage is the default target, so a plain build produces the image that
ships. The migration stage is selected explicitly by the job definition.

Why both stages come from one source: a migration must see the same models and
settings the application will run. If the job is built from a different tree, "what
migrated" and "what runs" are different code, and the divergence surfaces later as
a runtime error. A separate image, a separate branch, or a second build context is
not the same guarantee.

The migration stage is a job, not a service. It exits, it does not restart, and it
does not share the runtime image's entrypoint. See `deploying-backend-vps` for the
job and credential contract.

## Pin the base image

Pin the base by digest or by an immutable tag. A moving tag is an unverified
change of language patch level, distribution release, and system libraries. The
image can change without a commit, and every other pin in the project becomes a
claim about a base nobody selected.

Record why the pin exists in a comment. A future maintainer will otherwise "clean
up" the long tag back to a short one.

## The runtime identity

The runtime stage runs as a **non-root** user with a fixed, explicit uid and gid.

- Declare the values once, in one place, and consume them from the user creation
  and from every writable directory the service needs. A literal repeated in two
  places drifts, and the drift surfaces as a permission error on the first write.
- Prefer an identity outside the range reserved for system accounts, and do not
  rely on a name the base image happens to provide.
- No login shell and no home directory unless the service genuinely needs them.
- Create the writable directories and own them with that identity. A bind mount
  can shadow the ownership; the local definition must set the same owner.
- A read-only filesystem is a goal, not a default. Name every path the service
  writes, and make each one explicit.

## The final filesystem

The final stage carries runtime dependencies, not the tools used to install them.

- Install compilers, headers and build tools only for the dependency
  installation. Remove them in a later layer, after the install that needed them.
- Assert the removal. A silent `apt-get` failure or a dependency that pulls the
  compiler back in leaves the toolchain in the image while the build looks clean.
- Distinguish a package installed directly from a package pulled in as a
  dependency. A blanket autoremove can take the runtime library with the compiler;
  mark the runtime library as explicitly installed.
- Do not copy a package's contents into the working directory when the code uses
  absolute imports. Keep the package root the code expects, or the entrypoint will
  fail before it serves a request.
- Keep the dependency manifest and the install command together, so a rebuild
  resolves the same set the image was tested with.

## The healthcheck

A healthcheck that only proves the process is listening is not a readiness check
for the service. It passes while the application cannot import its settings, its
database driver, or a library loaded at module import time.

The healthcheck should exercise the application's own serving path:
an endpoint that requires the application to have imported successfully and to be
able to answer. Use a start period long enough for the real startup, and a timeout
short enough to fail a stuck process.

If a dependency is required before the service can answer, decide explicitly
whether the healthcheck covers it or whether a separate functional gate does. A
liveness check that reports healthy while every request fails is the failure the
gate exists to catch.

## What is never baked in

- A database DSN, an object-store credential, a signing key, or any secret.
- A value that differs between environments. Resolve it at runtime from the
  environment or the orchestrator.
- A hostname or port that belongs to another project on a shared estate.
- A production data file, a fixture, or a seed row.
- A development command, a debugger, a test runner, or a package manager the
  service does not invoke at runtime.

The same image is built once and promoted. If it needs a different value in a
different environment, that is configuration, not a second build.

## Verify the running container

The Dockerfile is a claim; the running container is the evidence.

1. Build both stages. A runtime build that succeeds while the migration stage is
   broken is not a passing build.
2. Run the application's import in the runtime image as the runtime user.
3. Inspect the configured user of the running container. Do not read `USER` from
   the Dockerfile text.
4. Assert that development tooling is not importable in the container.
5. Exercise a real request, not only the health endpoint. A functional gate that
   touches the database, the object store or another dependency is stronger than a
   port check.
6. Confirm a writable path actually accepts a write as the runtime identity.

## Stop and ask if

- the base image cannot be pinned;
- the service genuinely needs root, or a writable path outside the declared set;
- the runtime stage needs a compiler or a build tool to start;
- a secret would have to be baked in to make the image work;
- the migration stage and the runtime stage cannot share a source;
- the only available healthcheck proves the port and not the application.

## Checklist

- [ ] The base image is pinned by digest or immutable tag.
- [ ] One Dockerfile has `migrate` and `runtime` stages from the same source.
- [ ] The runtime stage is the default build target.
- [ ] The runtime user is non-root, with a fixed uid/gid declared once.
- [ ] Every writable path is explicit and owned by that identity.
- [ ] Build tooling is installed only for the dependency install and removed after.
- [ ] The final image carries no test runner, debugger or package manager.
- [ ] The healthcheck fails when the application cannot import or answer.
- [ ] No DSN, secret or environment-specific value is baked in.
- [ ] The running container's user and packages were verified, not the Dockerfile text.
- [ ] A functional request passed against the running image.

## Optional example

The shape below is an illustration, not a rule. Substitute the project's own
values and commands.

```dockerfile
FROM <base-image> AS migrate
WORKDIR <app-root>
COPY <dependency-manifest> .
RUN <install-command>
COPY <application-package> <app-root>/<application-package>
COPY <migration-directory> <app-root>/<migration-directory>
COPY <migration-config> .
CMD [<migration-command>]

FROM <base-image> AS runtime
WORKDIR <app-root>
ENV APP_UID=<uid> \
    APP_GID=<gid>
RUN <install-runtime-libraries>
RUN <install-build-tools> && <install-command> && <remove-build-tools>
RUN <create-runtime-user>
COPY <application-package> <app-root>/<application-package>
RUN mkdir -p <writable-path> && chown "$APP_UID:$APP_GID" <writable-path>
USER <runtime-user>
EXPOSE <port>
HEALTHCHECK CMD <health-command>
CMD [<runtime-command>]
```
