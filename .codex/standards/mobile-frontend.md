# Mobile Frontend Standards (generic stack conventions)

The discipline is in the `mobile-frontend-developer` persona. This file names the
stack a consumer opts into by selecting the `mobile` bundle. A consumer on another
mobile stack keeps every rule in the persona and replaces the nouns here.

## Layout

```
src/
  app/          shell: navigation, providers, theming
  features/     one directory per domain
  shared/       API client, credential storage, formatting, tokens
  stores/       client state containers
  types/        generated and hand-written types
  mocks/        structurally faithful fixtures
```

Group by feature, not by layer. `features/<domain>/` beats splitting `screens/`,
`hooks/` and `types/` three ways, because the second arrangement puts every change
in three directories and hides a feature's whole surface from a reader.

## Stack

- **Framework** — React Native with Expo. Expo modules where they exist; a bare
  escape hatch only where a requirement genuinely needs one, and said out loud.
- **Language** — TypeScript, strict. Reuse the generated types; a parallel
  interface for one payload drifts silently.
- **Navigation** — React Navigation, native stack with bottom tabs. Every screen
  reachable by platform convention, not only by a button.
- **Server state** — TanStack Query. It owns anything the server is authoritative
  about: fetched, cached, invalidated, refetched. The cache is the store; do not
  copy results into global state on arrival.
- **Client state** — Zustand. Session, preferences, draft input, navigation
  intent — written only by deliberate user action.
- **HTTP** — Axios behind one shared client. Base URL, auth header and error
  handling live there and nowhere else.

## Rules that recur

- Credentials are read from secure storage and nowhere else. Not from state that
  is persisted, not from a build-time constant.
- Every screen declares loading, empty, error and success. An empty result set is
  not a loading state, and showing a spinner forever is the usual symptom.
- Mocks are structurally faithful to the real schema and regenerated from the
  contract, never hand-maintained. List the features still mock-backed; that list
  is a statement about what has not been proven.
- No endpoint, route name or payload shape is assumed. Read the server's routes or
  its published schema, or mark the contract unverified and list what must be
  confirmed.
- Keep the client decoupled from the server repository while staying compatible
  with its contract. Shared types are generated, not copy-pasted.

## What the consumer decides

The API contract, the domain vocabulary, design tokens, the platforms shipped, and
whether the client shares a repository with the server or lives beside it. The
harness has no opinion on those and never writes them.
