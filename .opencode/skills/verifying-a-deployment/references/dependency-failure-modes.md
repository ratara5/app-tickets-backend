# Dependency Failure Modes

The failures a deployment gate will not catch unless it is looking for them
specifically. Each entry: what it looks like, why the obvious check passes, and what
actually finds it.

---

## 1. The signed-origin mismatch

**Looks like**: every client fails to load a resource the service generates a URL
for. Uploads, downloads, PDFs, images. The service's own requests keep working.

**Why the obvious check passes**: a reachability check succeeds. The service dials
its dependency over an internal address and every internal operation is fine. The
URL it *generates* is a different value, and that value is only resolved by the
client.

**Mechanism**: signed URLs are bound to a host. A URL signed for an internal name
is unusable by a client that cannot resolve that name, and a URL signed for an
address that moved is unusable after the move. Sometimes the mismatch is a *path*
rather than a host — an endpoint that includes an internal prefix the public proxy
does not serve.

**What finds it**: fetch a generated URL from outside the network, over the public
path, and read the bytes. Not a `HEAD` request, and not from inside.

**The general rule**: any application that hands a client a URL has **two**
addresses per dependency, and one of them is only ever tested by a client.

---

## 2. Two values for one dependency

**Looks like**: works on the host, fails in a container. Or works in staging, fails
in production. Or uploads work from the server and fail from the network.

**Why the obvious check passes**: each environment's own test suite passes, because
each is testing its own value.

**Mechanism**: one configuration value is doing two jobs — the address the service
dials, and the origin it embeds in URLs. They are the same only when the client and
the server share a network namespace, which is exactly the assumption that breaks
when either side is containerized.

**What finds it**: assert that the dialled address and the signed origin are
configured independently, and that both are correct **for the environment doing the
signing**. Reading the value the service resolved at startup, per environment, is
the check.

**The fix is a split, not a tuning**: one value for internal I/O, one for the public
origin. A single value forces one of the two to be wrong.

---

## 3. DNS that resolves on the host and not in the container

**Looks like**: the service starts normally, is fully healthy, and fails on the
first request that touches a dependency by name.

**Why the obvious check passes**: the health endpoint does not resolve the
dependency name, or resolves it from the host's resolver where a hosts-file entry or
a search domain makes it work.

**Mechanism**: a container name resolves only on the network the container is
attached to. A loopback address resolves to the container itself, not the host. A
name that works from a shell on the host is not necessarily resolvable from inside a
container, and a service that was developed on the host keeps the host's value.

**What finds it**: resolve every dependency hostname **from inside the running
container**, and confirm the container is attached to the network where those names
live. Also confirm the *shared* dependencies are attached to it — a container that
is not on the network cannot be reached no matter what your app is configured with,
and that step has to be redone whenever the shared container is recreated.

**The trap that makes this permanent**: moving a shared container to a different
compose project moves it to that project's network. The application is then
correctly configured and the shared container is simply not reachable. Nothing
reconnects it automatically, and the next recreate of the shared container
reintroduces the problem even after a manual fix.

## 4. Serialized URLs, correct values

**Looks like**: uploads work in one environment and 403 in another, with identical
configuration.

**Why the obvious check passes**: the endpoint resolves, the credentials are valid,
the request is well-formed. Everything is true and the request still fails.

**Mechanism**: many object stores sign the *region* as well as the host and the
date. A client and a service that both dial the same endpoint can still produce
mismatched signatures if their configured region differs, because the signature is
computed from configuration rather than discovered from the server.

**What finds it**: read back the region the service resolved, and confirm it is the
region the object store is actually serving. The value is often a default when it
is not configured, and a default that happens to be right locally is a default that
is wrong in another region.

---

## 5. Read-only filesystem, writable expectation

**Looks like**: startup is fine; the first upload, export, cache write or temporary
file fails with a permission error.

**Why the obvious check passes**: the process is healthy and every read works.

**Mechanism**: a hardened image commonly runs with a read-only root filesystem,
which is correct and desirable. Code that wrote to a path inside the image worked
before hardening and now fails. Often the first write in a long-running process, so
it appears hours after the deploy.

**What finds it**: exercise a write path during verification, not just reads. And
confirm the intended paths are mounted as writable volumes rather than assuming.

---

## 6. Environment variables that override the file

**Looks like**: the service starts with a missing or wrong value that is *present
and correct* in the environment file.

**Why the obvious check passes**: the file is right, and reading the file shows the
right value.

**Mechanism**: in most container runtimes, an explicit `environment:` entry
**overrides** the same key from an env file. An unset shell variable expanded in that
block becomes an empty string that beats a correct file value — and empty is a
valid-looking value for many parsers, so the service starts with no database host
rather than refusing to start.

**What finds it**: read what the process actually resolved, at startup, per
environment. Do not read the file. A common hardening is to make required values
fail loudly at container start when empty, so this class becomes a failed deploy
rather than a silent misconfiguration.

---

## 7. Chunked or staged writes lose their staging area

**Looks like**: uploads fail only after a restart, or only on large files, or only
under load. Small files are fine.

**Why the obvious check passes**: the upload succeeds in testing, and the small-file
path is the one that gets tested.

**Mechanism**: a multi-part upload stages bytes on local disk before completing. A
container without a volume for that path loses in-flight uploads on restart, while
the database rows describing them survive — so the records exist and the bytes do
not.

**What finds it**: complete an upload, restart the service, and confirm the
completed upload is still readable. Also check the threshold behaviour: a path that
only engages above a size limit is invisible to small-file testing.

---

## 8. Clock skew in signed requests

**Looks like**: intermittent authorization failures, worse on one node than another,
and worse shortly after a deployment.

**Why the obvious check passes**: the credentials are correct and the request is
valid, most of the time.

**Mechanism**: signed requests carry a timestamp and are rejected outside a validity
window. A node whose clock has drifted — a fresh VM, a suspended host, a container
sharing a host clock that was never checked — produces signatures that are valid
elsewhere and rejected here.

**What finds it**: compare the clock on every node that signs, against a reference.
This is a deployment-time check precisely because a drifted node looks healthy
until it signs something.

## 9. Schema drift between the code and the database

**Looks like**: a route that reads a field 500s, while most of the application works.

**Why the obvious check passes**: the health endpoint is fine, most endpoints are
fine, and the table exists.

**Mechanism**: the deployed code expects a column, type or constraint that the
database does not have. The reverse also happens: the database has a constraint the
code does not expect, so writes fail on data the code considered valid.

**What finds it**: compare the code's expected schema against the live database as a
gate, not as a one-time reconciliation. A reconciliation done once is correct on the
day it is done. And a table that exists is not the same as a table with the right
columns — assert the shape, not the count.

---

## 10. The dependency that is only reached in one code path

**Looks like**: a dependency outage that is invisible for hours, then sudden.

**Why the obvious check passes**: verification exercised the main path, which never
touches the optional dependency.

**Mechanism**: a queue, a cache, an analytics call, a webhook, a PDF renderer, a
notification service. The dependency is genuinely optional, so the main path is
unaffected and monitoring shows nothing.

**What finds it**: during verification, exercise **each** dependency at least once,
including the ones behind rarely-taken branches. If a dependency cannot be exercised
in the verification environment, that is a fact to record — not a gate to mark
passed.

---

## 11. Reverse proxy, when the container is fine

**Looks like**: everything works locally and inside the network; the public URL
fails, or fails intermittently, or serves the wrong thing.

**Why the obvious check passes**: every container-level check is green.

**Mechanism**: certificate expiry or renewal failure, an upstream that was
reconfigured, a routing rule that no longer matches, a body-size or timeout limit,
a header the proxy strips or adds. All of these are invisible from inside.

**What finds it**: verify from outside, over the public path, including TLS. And
verify the *proxy's* health endpoint separately, since a proxy can report its own
upstreams as healthy while routing traffic to the wrong one.

---

## 12. Retention removing the way back

**Looks like**: a rollback that should take seconds instead takes an hour, or fails.

**Why the obvious check passes**: nothing is wrong until it is needed.

**Mechanism**: cleanup policies, disk quotas, and log rotation all remove the
artifacts a rollback depends on — previous images, previous configuration, previous
migration state.

**What finds it**: before the release, confirm the previous artifact is still
present and pullable. After the release, confirm again. This is a two-second check
whose absence turns a five-second rollback into an incident.

## Pattern summary

| # | Failure | The check that catches it |
|---|---|---|
| 1 | Signed origin wrong for clients | fetch a generated URL from outside |
| 2 | One value serving two jobs | assert both are configured, per environment |
| 3 | Name resolves on host, not in container | resolve from inside the container |
| 4 | Region mismatch in signatures | read back the resolved region |
| 5 | Write to a read-only path | exercise a write, not only reads |
| 6 | Env block overrides the env file | read what the process resolved |
| 7 | Staging area lost on restart | complete an upload, restart, re-read |
| 8 | Clock skew breaking signatures | compare node clocks |
| 9 | Code and database disagree | assert schema shape as a gate |
| 10 | Rarely-used dependency unexercised | touch every dependency once |
| 11 | Proxy or TLS failure | verify from outside |
| 12 | Rollback artifact already gone | confirm the previous artifact exists |

**Eleven of these twelve pass every check that only asks whether the process is
running.** That is the argument for the functional layer in the main skill, and the
reason a health endpoint is not a verification strategy.
