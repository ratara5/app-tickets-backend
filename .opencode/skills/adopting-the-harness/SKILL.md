# Adopting the Harness

**Run this in the consumer**, on a migration branch. The canonical procedure is
the ADOPTION runbook that ships with the harness checkout
([docs/ADOPTION.md](../../docs/ADOPTION.md)); this skill is its agent entrypoint.
Read the runbook before acting and do not restate it — one owner per topic.

## Invocation

```
Use skill adopting-the-harness with harness path <path-to-harness-checkout>
```

The harness path is required unless the consumer already pins a release the
harness can resolve. If neither exists, stop and ask for one.

## The four phases, in this order

1. **Survey** — detect the consumer state from evidence and write
   `MIGRATION_PLAN.md` at the consumer root. Read-only.
2. **Learn gate** — ask once, after survey and before any deletion, whether the
   pre-harness material should be harvested. Record the answer either way.
3. **Install** — resolve one validated harness source, write `.agentic.yaml`,
   sync, `sync --check`, and commit the projection plus lock.
4. **Remove** — classify the legacy seed and delete only approved `IDENTICAL`
   regular files, in a separate commit.

A phase the detected state makes inapplicable is **skipped with its evidence
recorded**, never reported as completed. Do not reorder phases, and do not run
removal before a verified install.

## Essential safety stops

Stop before any write when:

- the working tree is dirty — take the local `cp -a` safety copy first;
- the `pre-agentic-layer` tag is not an ancestor of `HEAD`;
- the detected state is `UNKNOWN`;
- no harness source validates, or it disagrees with the consumer's pin;
- `agentic sync --check` is non-zero.

Stop before removal when:

- `MIGRATION_PLAN.md` lacks a durable learn decision or the plan/backup/
  provisional-classification approval;
- the classification has no applicable seed source;
- the classification is implausible (mostly `UNKNOWN`, no `IDENTICAL`).

## Approval boundaries

- Before install, the operator approves the migration plan, the backup, and the
  **provisional** `IDENTICAL` set. That approval authorizes nothing outside it.
- After install, classification is recomputed and the deletion set is its
  intersection with the approved provisional set; it may only shrink.
- `MODIFIED` paths may be salvaged, but are retained, and salvage needs its own
  diff approval.
- `SYMLINK` paths are handled only by the projection-time replacement procedure.
- `PROJECTED` and `UNKNOWN` paths are skipped and reported; `UNKNOWN` and
  `CONSUMER-OWNED` paths are never deleted.
- One validated harness source is used for both `sync` and classification, and
  the source, commit, and declared version are recorded in `MIGRATION_PLAN.md`.

## Learning is a handoff

A "yes" produces a prepared, read-only snapshot (made by the operator or CI with
`scripts/prepare-worktree-to-learn.sh`) and `HARVEST_REQUEST.md` at the consumer
root. The harness-side harvest consumes them. This procedure never writes the
harness repository, never writes `docs/` or `openspec/`, and never moves an
existing `pre-agentic-layer` tag.

## Deliver

Report the detected state, the harness source and version, each phase as done or
skipped with evidence, the approvals obtained, the snapshot path if requested,
and the rollback command. Include the fields the harness needs to register the
operation: date, consumer, baseline, harness version, outcome, and the record
reference `consumer:MIGRATION_PLAN.md`. This session does not write the harness,
so the operator or the harness-side session writes the register row. The removal
commit is separate so it can be reverted on its own; the `pre-agentic-layer` tag
is the durable fallback.
