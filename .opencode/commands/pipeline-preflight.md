# Pipeline Preflight

Run this before implementation and before applying a change. It answers one
question: **is it safe to proceed right now?**

If any check fails, stop and report it. Do not continue and mention it later —
a preflight failure discovered halfway through is a change to unwind.

## Usage

```
/pipeline-preflight [stage] [gate-command]
```

`stage` is optional; without it run the defaults, which cover starting work.

`gate-command` is optional. When given, run it instead of looking one up. When
absent, use the gate command the consumer's standards declare — commonly a single
target (`make gate`, `npm run check`, `just verify`). If the consumer declares
none, run the consumer's test command and say in the report which one you chose
and why. Never guess silently: a preflight that ran nothing and reported success
is worse than no preflight, because it is trusted.

## What it runs

The consumer's automated gates, cheapest first. Ordering is not a style
preference: a formatter that takes two seconds should not sit behind a suite that
takes ten minutes, because a slow gate queue is a gate people stop waiting for.

1. Format and lint — seconds, catches most mistakes.
2. Types — catches the class of error that looks right.
3. Unit tests — the tier that must pass before anything else means anything.
4. Integration or contract tests — the tier that needs a real dependency.

The first failure is the report. Do not run tier four because tier one was fast.

## Manual checks

Automation does not cover these, and in practice this is where preflight fails:

- [ ] **The specification is current.** The artifacts reflect the request as it
      stands now, not an earlier version of it.
- [ ] **No work is already in flight.** Another change is open with tasks in
      progress, or this one already has a branch with commits. Two open changes
      editing one file is a conflict neither author saw coming.
- [ ] **The change is scoped.** The diff touches the files the change names. A
      diff wider than the change describes is the signal that the change is
      underspecified — go back to the artifacts, not forward into the code.
- [ ] **Dependencies are available.** Whatever the work needs to run is reachable
      now, so a failure is unambiguous rather than a missing service.
- [ ] **The rollback is written down.** Before the change, not reconstructed
      afterwards when it is needed.
- [ ] **Nothing generated has been hand-edited.** No file carrying a `GENERATED`
      header has local modifications. If one has, sync is the fix; the edit is
      not.

## Reporting

```
## Preflight — <stage>

  format    ✓ <n> files
  types     ✓ clean
  tests     ✓ <n> passed
  contract  ✓ <n> items

  Manual:
    specification current   ✓ / ✗
    no work in flight       ✓ / ✗
    scope is bounded        ✓ / ✗
    dependencies available  ✓ / ✗
    rollback written        ✓ / ✗
    no generated edits      ✓ / ✗

Verdict: PROCEED | BLOCKED
<for BLOCKED: what failed, and what unblocks it>
```

`PROCEED` is a claim. Every tick above it is a fact someone can check later.
